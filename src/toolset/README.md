## Responsibilities

- `startToolset({ version, tools? })` (`main/server.ts`, ADR-0023) serves the shared toolset on an ephemeral loopback port at `/mcp`, using the MCP SDK's stateless HTTP transport. Transport instances are per POST; authority, work and cancellation are not. Exact Host, no-Origin and bearer-credential checks precede MCP handling; GET and DELETE are refused.
- Bound access: app composition supplies `RunningToolset.sessions` to `SessionHost`. `bind` establishes the app owner, canonical workspace and effective policy before provider startup, and returns a `SessionAutomation` lifecycle port plus that owner's `Toolset` factory. `open` rotates the access generation; obsolete factories and credentials cannot recover authority or revoke a replacement's access. Credentials stay in memory and never enter UI data, records or model arguments.
- `main/broker.ts` owns operations, approvals, grants and deadlines. Auto asks for shared tabs, application observation/actions, foreground control and dialogs; isolated browsing, metadata and presentation do not ask. Yolo skips only questions. The owner-scoped host answer path accepts the existing approval answers and never consumes a provider approval. End, Stop, takeover, policy changes, turn end and access revocation cancel affected queued work; session grants survive turn end but not target/session end.
- `main/resources.ts` allocates opaque owner-bound handles and observations. Target kind and generation, document/geometry generations and application ownership are checked again after approval and queueing. Targets declare whether their operation may activate them when registered; action plans cannot exceed that declaration. A shared profile never transfers a tab's ownership. Session close deletes isolated resources through their release port and detaches shared/external ones, without closing user tabs or applications.
- Target summaries contain `iconId`, never icon bytes. `main/icons.ts` checks backend-supplied PNG bytes at registration, including signature, actual header dimensions, chunk checksums and bounded scanlines. Invalid or over-budget icons are omitted without rejecting the target. Content hashes share one stored image across facts and sessions. The UI's `icon` read requires a retained resource, grant, approval or call fact in that session to name the ID; another session's cache entry is not authority. Reads and registrations reclaim unreferenced holdings, and session removal releases its holdings. The UI can cache a read by the stable ID.
- `main/policy.ts` enforces read-only before approvals and canonical workspace/owned-temporary file bounds independently of mode. Missing destinations, traversal and existing or dangling symlinks cannot widen workspace-write for writes and picks. Read intents remain subject to the file-serving feature's existing permissions. Executors receive rechecked canonical paths and must constrain their actual file mechanism; unverifiable native pickers are refused. The production binding currently supplies no additional temporary roots; app composition must allocate any extra owned temporary roots at binding; an executor cannot widen the scope.
- `main/scheduler.ts` serializes mutations by backend target/application and explicit foreground or activation-prone mutations through the desktop lane. Cancellation before dispatch has no effects; after dispatch it is indeterminate until the backend settles. Returning a timeout does not release the lease or replay input. A timeout or uncertain result remains deduplicated across access changes.
- `main/activity.ts` keeps bounded call records before policy/setup/argument refusals. Browser/computer records carry target, sharing, delivery and frame metadata; `frames` and the UI port's `callFrames` fetch image bytes only for calls being displayed. Eviction preserves capture geometry/time and marks bytes unavailable. Panel summaries contain each item's content and box, or null for a closed panel, with the presentation's version. Pending presentation notices coalesce by presentation; a validated tool-result receipt or accepted separate turn context retires only the version it carried, never a newer state. Retained delivered versions remain deduplicated. Reading, failed sends and reconnect do not consume notices.
- Refused outcomes can name a per-call setup requirement, an availability reason, a bounded denial message or the exact panel refusal and current presentation. Setup refusals remain in their call records; they do not leave the session in a stale waiting phase. Setup ports include Safari's named profiles and browser versions and the user-only extension/site-access actions.
- A call keeps its approval request, answer/time and grant link, operation and grant endings, and bounded timestamped incidents. Executors report activation, dismissed dialogs and Secure Input through their call context; target and operation come from the broker. Takeover is retained on the operation's latest call. These facts survive renderer reload within the record-retention window.
- `AutomationEvent` states how each event affects a snapshot. A `state` event contains `AutomationLiveState` only: policy, phase, resources, operations, grants, pending approvals, foreground owner and availability. Initial/resynchronization snapshots add the history. Call records change only through `tool-call`/`tool-call-removed`, ended grants through `grant-ended`/`grant-end-removed`, and pending notices through `presentation-notices`. The pure `sessions/shared/automation-state.ts` fold preserves untouched history by reference; the fake follows the same rule. Epoch changes and sequence gaps require resnapshotting. Fakes support seeded capabilities, on-demand frames/icons and deliberate sequence gaps.
- The sessions hook supplies `HostTurnContext` independently of user text. Only an adapter advertising `supportsHostContext` can acknowledge that route; existing adapters leave it pending until their context integration lands. The user's message and its displayed history are never rewritten to contain transport metadata.
- MCP tools shipped now: `automation_capabilities`, which reads cached tool capabilities and effective policy without starting a backend. App-composed `AutomationTool` definitions supply schemas, conservative plans and executors for later feature tools. The SDK validates MCP envelopes; the broker validates feature arguments after allocating their receipt, so invalid arguments also have activity records. JSON schemas are compiled/checked once at startup. Cancellation notifications on a separate POST reach the original owner/generation's work.

## Not responsible for

- Browser engines, external connections, native processes, OS permissions or renderer layout. None is started by capability discovery or by these contract tests.
- Provider protocol configuration, native-ID translation, receipt normalization or host-context delivery: adapters implement those against the sessions interface. Codex receives its initial bound factory through start/resume options; complete reconnect/receipt/context integration across providers follows separately.
- Rendering approvals, setup or activity. The UI ports and controllable fakes are available; IPC consumers, feature tool registration and persistent automation-history integration are separate work. `callRecord` looks up the same 256 retained records as the snapshot, not an unbounded archive. After record eviction or app restart, only the provider's own history entry remains; the UI must not invent screenshots, sharing/delivery details or Show for a missing record. Retained records survive provider/renderer reconnect in the running app.

## Interface

- `main/server.ts`: `RunningToolset` exposes `name`, `broker`, `sessions` and `close`. There is no unbound `open` method.
- `main/broker.ts`: `AutomationBroker`, for app composition and trusted backend registration/lifecycle only. `BrokerAccess` is verified by object identity held in a private registry, never by its visible generation alone. MCP execution reaches only `dispatch` and cached capabilities through a bound access; user/setup/lifecycle ports are not registered as model tools.
- `main/execution.ts`: `AutomationTool`, `ExecutionPlan`, `ExecutionContext` and bounded `ExecutionResult`; plans are trusted feature code, not model-selected effects, setup needs, operation kinds or lock keys. The optional plan `setup` names a specific unmet requirement without starting setup. Executors honor cancellation and settle only once effects have stopped. Their `report` retains an incident with the current call. A later native integration must not resolve its promise while injected input can continue.
- `shared/automation.ts`: `AutomationBridge`, `UserSetupBridge` and `SetupAction`; common facts live in `sessions/shared/automation.ts`. `shared/automation-fake.ts` provides controllable UI-only fakes that start no services and prove no authority.

## Dependencies

- Sessions' main interface and shared model, the MCP SDK, zod and Node.js built-ins; no provider implementation, renderer or Electron import.
- Only app composition, this module and the provider live-test composition may import it under the current dependency rules. The existing `toolset-only-to-sessions-contract` and `toolset-only-from-app` rules remain unchanged. Feature type-only edges will be added with their consumers, not as broad exceptions in advance.

## Invariants

- Authority comes from the app session and bound access, never native provider IDs, model arguments, resource labels or receipts.
- Checks run after every asynchronous approval/queue/file check and immediately before dispatch. An executor receives no setup or permission-changing port.
- Identical action IDs reuse the recorded outcome; changed arguments conflict. The action-ID ledger retains tombstones after a result is evicted, returning `result-expired` rather than executing again.
- Initial bounds: 32 active calls per owner, 128 resources, 256 retained call records/observations/ended grants, 4096 distinct action IDs, 128 scheduler waiters, 60 s call deadlines and 10 min operation deadlines. Calls hold at most four frames, together at most 8 MiB in base64 and 4096 px on each edge; retained images have a 16 MiB per-owner budget and explicit eviction state. Image signatures, receiver metadata and finite geometry are checked before publication. Ordinary result JSON is bounded to 64 KiB; feature schemas may declare argument budgets up to 16 MiB, defaulting to 256 KiB, measured in UTF-8. Capability discovery advertises these bounds, and the SDK HTTP body cap includes envelope overhead.
- `AUTOMATION_ICON_LIMITS` allows PNG only, at most 64 KiB decoded and 128 px on either edge, with 256 distinct icon holdings per session. Repeated bytes consume one holding; a new target past the budget registers without an icon. Icon data is separate from screenshot retention and never appears in state events or snapshots.
- At most 256 pending presentation notices, 4096 presentation-version receipts and 32 sends awaiting acceptance are retained. Receipts beyond the bound are evicted in last-change order, excluding presentations with a pending notice, so the receipt limit is not a lifetime quota. Deduplication covers retained receipts; the relay owns current versions and its bounded transport lifetime. Each notice must fit the JSON-result bound. A producer receiving `limit-exceeded` for pending notices must retain/retry its report; the broker never calls it delivered or silently drops an existing notice. Each call retains up to 64 incidents; a denial message has at most 2048 UTF-16 code units, with oversized answers refused while their approval stays pending.
- Unit tests use synthetic handles, images, filesystem roots, deferred executors and fake providers. The HTTP tests use only loopback MCP and verify cross-POST cancellation; no browser, GUI, helper or real model is needed.
