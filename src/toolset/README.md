## Responsibilities

- `startToolset({ version, tools? })` (`main/server.ts`, ADR-0023) serves the shared toolset on an ephemeral loopback port at `/mcp`, using the MCP SDK's stateless HTTP transport. Transport instances are per POST; authority, work and cancellation are not. Exact Host, no-Origin and bearer-credential checks precede MCP handling; GET and DELETE are refused. Its instructions, which every provider shows its agent whatever it defers behind its tool search, map the tools by group and name and say when the session tools beat a provider's own subagents. Every tool goes out with its MCP annotations (`ToolEffects` in `main/execution.ts`): whether it only reads, may change or end what it acts on, does nothing more when repeated, and reaches the web (docs/conventions.md, Built-in tools).
- Bound access: app composition supplies `RunningToolset.sessions` to `SessionHost`. `bind` establishes the app owner, canonical workspace and effective policy before provider startup, and returns a `SessionAutomation` lifecycle port plus that owner's `Toolset` factory. `open` rotates the access generation; obsolete factories and credentials cannot recover authority or revoke a replacement's access. Credentials stay in memory and never enter UI data, records or model arguments.
- `main/broker.ts` owns operations, approvals, grants and deadlines. Auto asks for shared tabs, application observation/actions, foreground control and dialogs; isolated browsing, metadata and presentation do not ask. Yolo skips only questions. The owner-scoped host answer path accepts the existing approval answers and never consumes a provider approval. End, Stop, takeover, policy changes, turn end and access revocation cancel affected queued work; session grants survive turn end but not target/session end.
- MCP initialization supplies shared guidance on choosing a browser or native target, using the app's browser for isolated or app sharing and the connected Chrome profile for global sharing, grouping calls under one operation and presenting results only when a user needs them.
- `main/resources.ts` allocates opaque owner-bound handles and observations. Target kind and generation, document/geometry generations and application ownership are checked again after approval and queueing. Targets declare whether their operation may activate them when registered; action plans cannot exceed that declaration. A shared profile never transfers a tab's ownership. Session close deletes isolated resources through their release port and detaches shared/external ones, without closing user tabs or applications.
- Target summaries contain `iconId`, never icon bytes. `main/icons.ts` checks backend-supplied PNG bytes at registration, including signature, actual header dimensions, chunk checksums and bounded scanlines. Invalid or over-budget icons are omitted without rejecting the target. Content hashes share one stored image across facts and sessions. The UI's `icon` read requires a retained resource, grant, approval or call fact in that session to name the ID; another session's cache entry is not authority. Reads and registrations reclaim unreferenced holdings, and session removal releases its holdings. The UI can cache a read by the stable ID.
- `main/policy.ts` enforces read-only before approvals and canonical workspace/owned-temporary file bounds independently of mode. Missing destinations, traversal and existing or dangling symlinks cannot widen workspace-write for writes and picks. Read intents remain subject to the file-serving feature's existing permissions. Executors receive rechecked canonical paths and must constrain their actual file mechanism; unverifiable native pickers are refused. The production binding currently supplies no additional temporary roots; app composition must allocate any extra owned temporary roots at binding; an executor cannot widen the scope.
- `main/scheduler.ts` serializes mutations by backend target/application and explicit foreground or activation-prone mutations through the desktop lane. Cancellation before dispatch has no effects; after dispatch it is indeterminate until the backend settles. Returning a timeout does not release the lease or replay input. A timeout or uncertain result remains deduplicated across access changes.
- `main/activity.ts` keeps bounded call records before policy/setup/argument refusals. Browser/computer records carry target, sharing, delivery and frame metadata, and a browser record whether a panel showed its tab as the call was made (`inPanel`), which the plan takes from the presentation host; `frames` and the UI port's `callFrames` fetch image bytes only for calls being displayed. Eviction preserves capture geometry/time and marks bytes unavailable. Panel summaries contain each item's content and box, or null for a closed panel, with the presentation's version. Pending presentation notices coalesce by presentation; a validated tool-result receipt or accepted separate turn context retires only the version it carried, never a newer state. Retained delivered versions remain deduplicated. Reading, failed sends and reconnect do not consume notices. Deliveries batch notices within the JSON budget, retaining the rest for later calls/turns; app composition retries producer backpressure before each delivery opportunity.
- Refused outcomes can name a per-call setup requirement, an availability reason, a bounded denial message or the exact panel refusal and current presentation. `sandbox-denied` carries `{ kind: 'sandbox', level }` from the policy used by that call. An invalid `actionId` keeps `invalid-request` and adds `{ kind: 'argument', field: 'actionId', reason }`, with `required`, `invalid-type`, `too-short` or `too-long`, so a model can correct it. The result and retained call carry the same codes, never the invalid value. Feature execution has yet to start. Setup refusals remain in their call records and the session clears its waiting state. Setup ports report Chrome's installed version, profiles and connection state. Only the user starts setup.
- A call keeps its approval request, answer/time and grant link, operation and grant endings, and bounded timestamped incidents. Executors report activation, dismissed dialogs and Secure Input through their call context. The broker supplies the target and operation. MCP replies include dismissed dialog types as `dialogDismissals` when the call recorded them. Takeover is retained on the operation's latest call. These facts survive renderer reload within the record-retention window.
- After argument validation, `browser_act` and `computer_act` records carry `browserAction` and `computerAction` respectively, including for refusals and cancellations. Control labels come from current owner-scoped observations and use at most 100 UTF-16 code units. A named window change keeps its kind. Matching action ID replays reuse the retained facts. Input values and coordinates stay in execution arguments.
- `AutomationEvent` states how each event affects a snapshot. A `state` event contains `AutomationLiveState` only: policy, phase, resources, operations, grants, pending approvals, foreground owner and availability. Initial/resynchronization snapshots add the history. Call records change only through `tool-call`/`tool-call-removed`, ended grants through `grant-ended`/`grant-end-removed`, and pending notices through `presentation-notices`. The pure `sessions/shared/automation-state.ts` fold preserves untouched history by reference; the fake follows the same rule. Epoch changes and sequence gaps require resnapshotting. Fakes support seeded capabilities, on-demand frames/icons and deliberate sequence gaps.
- The sessions hook supplies `HostTurnContext` independently of user text. Only an adapter advertising `supportsHostContext` receives that route and its separate acceptance/failure callbacks. Native confirmation retires notices; queueing, unsupported context delivery and failed sends leave them pending. The user's message and its displayed history are never rewritten to contain transport metadata.
- Session tools (`main/session-tools.ts`, ADR-0036, ADR-0041): `session_list`, `provider_list`, `session_start`, `session_end`, `message_send` and `message_read`, served beside the automation tools but outside the broker, since they act on the app's sessions, once app composition gives the sessions' `SessionCoordinator` (`startToolset({ coordinator })`). Each is called with the owner of the calling access, which the server keeps by the access object, never with a session named in its arguments; `provider_list` and `session_start` are offered only to a session that may start sessions, and a call to either from a child is refused all the same. `provider_list` gives the coordinator's `providers`, each provider's models as a child of the caller would get them or why it could not list them, as text with each model's id, name, reasoning effort levels and defaults, and as structured content; `session_start`'s description points to it, and its model and effort arguments say that the coordinator refuses one the child's provider does not list. `session_start`'s provider argument describes every provider by the same two facts, who makes the models it runs and their family, and adds that each may offer other makers' models its account or settings add, so that an agent asked to have a model do some work can choose the provider behind it, which a provider's id, such as `antigravity`, does not always say; the module does not compile without those facts for every provider. It names the providers by their ids alone, as agents do: their names are the i18n catalogs'. Arguments are validated against each tool's schema; a refusal returns the reason as an error result. Every result of the app's tools, automation ones included, carries the notices of the session's new messages in an `inbox` field, in text after a session tool's own text and in the JSON of the others, which the coordinator then marks told; there and in `message_read`'s text, a report of the app's own on a child (ADR-0042) is called the app's report on the child, rather than a message from it.
- MCP tools registered by the app: `automation_capabilities` and `panel_list`, `panel_present`, `panel_update`, `panel_arrange`, `panel_close`, and the session tools. Capability discovery starts no backend. Panel mutations await the presentation host and return renderer-unavailable until a renderer connects; the close tool accepts presentation IDs only, leaving terminals to the user. Lists paginate retained owner-scoped state, and artifacts become bounded owner-scoped handles before reaching the renderer. App-composed `AutomationTool` definitions supply schemas, conservative plans and executors for later feature tools. The SDK validates MCP envelopes; the broker validates feature arguments after allocating their receipt, so invalid arguments also have activity records. JSON schemas are compiled/checked once at startup. Cancellation notifications on a separate POST reach the original owner/generation's work.

## Not responsible for

- Browser engines, external connections, native processes, OS permissions or renderer layout. None is started by capability discovery or by these contract tests.
- Provider protocol configuration, native-ID translation, receipt normalization or host-context delivery: adapters implement those against the sessions interface. Each adapter rotates its bound access on process replacement, normalizes receipts only from this toolset's native result envelope and reports provider availability; the bound access supplies owner, current turn and generation for validation.
- Rendering approvals, setup or activity. The UI ports and controllable fakes are available; app composition implements the automation and presentation IPC ports, and the panel renderer consumes acknowledged commands. Activity UI integration and persistent automation history remain separate work. `callRecord` looks up the same 256 retained records as the snapshot, not an unbounded archive. After record eviction or app restart, only the provider's own history entry remains; the UI must not invent screenshots, sharing/delivery details or Show for a missing record. Retained records survive provider/renderer reconnect in the running app.

## Interface

- `main/server.ts`: `TOOLSET_NAME`, the toolset's name, from the sessions module's `shared/tools.ts`, where the adapters and the activity read it too. `RunningToolset` exposes `name`, `broker`, `sessions` and `close`. There is no unbound `open` method. `startToolset` takes the automation tools and, as `coordinator`, a function that gives the sessions' coordination once it exists.
- `main/session-tools.ts`: `sessionTools` and `SessionTool`, for the server.
- `main/broker.ts`: `AutomationBroker`, for app composition and trusted backend registration/lifecycle only. `BrokerAccess` is verified by object identity held in a private registry, never by its visible generation alone. MCP execution reaches only `dispatch` and cached capabilities through a bound access; user/setup/lifecycle ports are not registered as model tools. The broker publishes the active native control or self-activation notice to main and each owner's paused target references to its page. Secure Input and human takeover have separate pause reasons. The app's stop shortcut interrupts the controlling session. Backend settlement releases the application and desktop claims.
- `main/execution.ts`: `AutomationTool`, `ExecutionPlan`, `ExecutionContext` and bounded `ExecutionResult`; plans are trusted feature code, not model-selected effects, setup needs, operation kinds or lock keys. The optional plan `setup` names a specific unmet requirement without starting setup. Executors honor cancellation and settle only once effects have stopped. Their `report` retains an incident with the current call. The native executor keeps its lease until a helper reply establishes settlement or the child has terminated.
- `shared/automation.ts`: `AutomationBridge`, `UserSetupBridge` and `SetupAction`; common facts live in `sessions/shared/automation.ts`. `shared/automation-fake.ts` provides controllable UI-only fakes that start no services and prove no authority.

## Dependencies

- Sessions' main interface and shared model, the inbox's block among it, the MCP SDK, zod and Node.js built-ins; no provider implementation, renderer or Electron import.
- Only app composition, this module and the provider live-test composition may import it under the current dependency rules. The dependency rules allow type-only edges to `panels/shared/presentation.ts` and `presentation-host.ts`; app composition supplies the executor and exact limit constants. Runtime imports into the panel implementation and renderer remain forbidden.

## Invariants

- Authority comes from the app session and bound access, never native provider IDs, model arguments, resource labels or receipts.
- Checks run after every asynchronous approval/queue/file check and immediately before dispatch. An executor receives no setup or permission-changing port.
- An action ID is optional (ADR-0045). A call without one is keyed by its tool and arguments where the tool changes something, so that a resend within its turn gets the first call's outcome, and runs afresh where the tool only reads (`readOnlyHint`). A tool's result can carry a second step (`NextStep`) on the target its first step made, as `browser_open`'s navigation of the tab it opened: the broker describes it on the call's record and performs it as any plan, its approval included, within the same call, and undoes the first step when the second is not verified.
- Within a turn, identical retained action IDs reuse the recorded outcome; changed arguments conflict. A turn's start drops the earlier turns' conclusively settled IDs, since a provider retries a call only within its turn: an agent that numbers its actions afresh in a later turn makes new requests, rather than getting the last turn's results back or conflicts with them. The action-ID ledger retains tombstones after a result is evicted, returning `result-expired`. At capacity it evicts the oldest conclusively settled ID; an ancient evicted ID is a new request. Running, dispatched, partial and indeterminate effects stay pinned across turns and reconnects, even after their activity record expires, rather than risking replay: a later turn's exact repeat of such a call gets its outcome back, while another call under its ID is a new request, which takes the ID over. If every slot is pinned, new work returns `limit-exceeded`.
- Initial bounds: 32 active calls per owner, 128 resources, 256 retained call records/observations/ended grants, 4096 retained action IDs, 128 scheduler waiters, 60 s call deadlines and 10 min operation deadlines. Neither counts the wait for the user's answer to an operation's approval, which has no limit: a call's deadline holds while its approval waits and starts again once allowed, and an operation's runs from its allowance. The binding gives providers `TOOLSET_CALL_TIMEOUT_MS`, a day, as `Toolset.callTimeoutMs`, so that their own tool-call limits leave the user time to answer. `SessionAutomation.onWaiting` reports since when the session's oldest approval has waited, from the broker's live state. Calls hold at most four frames, together at most 8 MiB in base64 and 4096 px on each edge; retained images have a 16 MiB per-owner budget and explicit eviction state. Image signatures, receiver metadata and finite geometry are checked before publication. Ordinary result JSON is bounded to 64 KiB; feature schemas may declare argument budgets up to 16 MiB, defaulting to 256 KiB, measured in UTF-8. Capability discovery advertises these bounds, and the SDK HTTP body cap includes envelope overhead.
- `AUTOMATION_ICON_LIMITS` allows PNG only, at most 64 KiB decoded and 128 px on either edge, with 256 distinct icon holdings per session. Repeated bytes consume one holding; a new target past the budget registers without an icon. Icon data is separate from screenshot retention and never appears in state events or snapshots.
- At most 256 pending presentation notices, 4096 presentation-version receipts and 32 sends awaiting acceptance are retained. At the send bound the oldest delivery token is retired as failed while its notices remain pending, allowing the next user message through. Merged turn context keeps only each presentation’s latest version within 64 KiB including its wrapper; native acknowledgements retire only the selected versions prepared for that delivery. Receipts beyond the bound are evicted in last-change order, excluding presentations with a pending notice, so the receipt limit is not a lifetime quota. Deduplication covers retained receipts; the relay owns current versions and its bounded transport lifetime. Each notice must fit the JSON-result bound. A producer receiving `limit-exceeded` for pending notices must retain/retry its report; the broker never calls it delivered or silently drops an existing notice. Each call retains up to 64 incidents; a denial message has at most 2048 UTF-16 code units, with oversized answers refused while their approval stays pending.
- Unit tests use synthetic handles, images, filesystem roots, deferred executors and fake providers. The HTTP tests use only loopback MCP and verify cross-POST cancellation, and the session tools against a fake coordinator; no browser, GUI, helper or real model is needed.
