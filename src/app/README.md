## Responsibilities

- Lifecycle (`main/index.ts`): once Electron is ready, it starts the toolset (ADR-0012) and composes the feature modules: the providers, which are Claude Code, Codex with the toolset, offered only when the toolset starts, and Grok Build with a `grok-build` folder in the app's data for its unpacked binary; the sessions module's host with them and with the records of the sessions the app starts, kept in the app's data, which later runs list, show and resume, with its confirmations and a session's menu as the window that asked draws them (the prompts), and the settings each folder's sessions last used, kept there too; the workspaces, kept there too, with their trust question and menu drawn the same way; and the files module's service, which takes the workspaces' folders, with its question before a panel with unsaved changes closes, drawn the same way. Every window it opens asks before it closes while its editors hold unsaved changes. Run unpackaged, the app shows its icon in the Dock itself (`resources/dock-icon.png`), as a packaged app's bundle carries it. The sessions waiting on the user show as the Dock icon's badge, and the icon bounces once when one more starts waiting while no window of the app has focus (the approvals module's `dockAttention`). Then it serves the bridge and opens the main window, and opens it again when the Dock icon is clicked while no window is open. The app keeps running without windows until the user quits it, as macOS apps do; quitting first closes the sessions, with their provider processes, and the toolset, waiting five seconds at most.
- The main process's language: the locale and then macOS's preferred languages, so that a `--lang` switch applies as it does to the page (DOC-mod-i18n).
- The main window (`main/window.ts`): a hidden-inset title bar with the native traffic lights, set 13pt from the top so that they are centred in the page's 40px title bar, on one line with what the page shows beside them and in the panels' headers, and a renderer with context isolation, the OS sandbox and no Node.js integration, into which the preload script loads the bridge. Under `electron-vite dev` it loads the renderer dev server; otherwise, and always when packaged, the built page.
- Navigation: the window opens no other windows and never leaves the app's page. Links to `http:` and `https:` URLs open in the default browser (`main/links.ts`); other links are dropped.
- The preload bridge, the page's only way to the main process:
  - The contract (`shared/bridge.ts`): `Bridge`, one part per feature module, each the interface that module declares in its `shared/` folder (`workspaces`, `sessions`, `panels`, `files`, `approvals`), and `prompts` (`PromptsBridge`), this module's own, the prompts the page is to draw and its answers to them; and the IPC channel of each call and notification.
  - The page's side (`preload/`): the preload script, built as one CommonJS file since the page is sandboxed, gives the page `window.bridge` (`createBridge` in `preload/bridge.ts`): a function for each call and a subscription for each notification, never Electron's own objects. A dropped item reaches the main process only as the path of a file the page was given, which the preload script finds with Electron's `webUtils`.
  - The main process's side (`main/bridge.ts`): `serveBridge` answers each call through the feature module that owns it, after checking that the call comes from the main frame of an app window showing the app's own page and that its values have the call's shapes (zod); anything else is refused. What the modules report goes to every window. Files dropped from the Finder become open to the editors as the panel area learns of them, and a window's watched files are forgotten when it goes.
- The prompts (`main/prompts.ts`, ADR-0013): `windowPrompts` implements the ui module's `Prompts` for a window, through which the feature modules' menus and questions go: each goes to the window's page with an id of its own, and `answerPrompt` takes the page's answer, provided it comes from that page and is one the prompt offers; while the window is gone, or once its page goes or loads anew, a menu resolves with no choice and a question with its cancel answer. The folder picker, the save panel and the question before a window whose editors hold unsaved changes closes stay macOS's own.
- The renderer (`renderer/`): the page with its content security policy. `main.tsx` starts the i18n module and renders the window shell (`app.tsx`) with the bridge: a full-height 220px sidebar, which ⌘B hides and shows, with the app's name in bold just below the title bar, then the workspaces module's Workspaces section, a thin line as wide as their rows, and the sessions module's Sessions section, which offers the workspaces as filters; beside it the main area, which holds the panels module's panel area, blank until something opens in it. The workspaces' tree rows drag into the panel area in the panels module's drag format, and a row opened from the keyboard opens there too, to the right of the focused panel, or for a file already open, focuses its panel. Files open in the files module's editors, which give their panels an unsaved mark and are asked before their panels close. New session opens a session page, the sessions module's, in the selected workspace's folder or, while there is none, the day's folder in `~/3mukon-code`, which the bridge makes when a session starts there; a session clicked in either list shows in its panel or opens in one. A session's menu, at a secondary click on it in either list, archives, unarchives or removes it, and the panels of a session removed from the lists close; the Sessions section lists the sessions that are not archived, and the archived list, told how many are archived, loads them only as it opens. Session pages and sessions fill their panels, titled by the session's title or else its provider once it runs, with its status: as the Sessions list shows the session, or else as the main process gives the sessions the window has shown that the list does not hold, such as an archived one, or until then as the archived list showed one opened from it; a page whose first message starts its session becomes that session's panel. As the window opens, the shell has the sessions module ask for what session pages offer (`preloadOffers`), so that a page shows its provider's models as it opens. The window's top 40px form its title bar, which moves the window, shows no title and has no line beneath it: in the sidebar, the row of the window buttons; over the main area, the headers of the panels at the top, or an empty strip while none is open. Just after the window buttons, wherever they lie, the sessions module's archived list keeps its button's place, and just after it the approvals module's waiting button counts the sessions waiting on the user, and shows the one that has waited longest in its panel, with the focus on its oldest waiting request, as ⇧⌘A does from anywhere in the window, going on to the next waiting session at each press; session pages show their approvals and questions with the approvals module's view, which answers them through its part of the bridge. The sidebar's divider runs through it, and while the sidebar is hidden the window buttons lie over the main area, where the panel area leaves room for them. The menus and questions the main process asks show over the window, one at a time in the order asked, drawn by `PromptHost` (`renderer/prompt-host.tsx`) with the ui module's `Menu` and `QuestionDialog`, and each answer goes back: a menu where the pointer or the keyboard last asked for one, as a secondary click, the menu key or VoiceOver's menu command does, and otherwise under the element with the focus; a question over the window. The page itself never scrolls; its panes and lists scroll within themselves (L-0001). The ui module's paper grain lies over the window's background, behind everything on it.
- The application menu, which is Electron's default macOS menu for now.

## Not responsible for

- Feature UI and state, such as workspaces and sessions: each lives in the feature module that owns it, and this module only composes them. The session pages and the waiting indicator join the shell from the modules that own them, built from the ui module's components.
- What a bridge call does: the feature module behind it decides, and declares the call in its `shared/` contract.
- Packaging, which `electron-builder.yml` and `scripts/package.sh` configure for the whole repository, with the app's icon in `resources/`, which `scripts/app-icon.sh` makes from a square picture: the picture as a full square in `icon.icns`, which macOS cuts to its own icon shape, and in macOS's icon shape in `dock-icon.png`.

## Interface

None: this module is the entry point, and no other module imports it. Feature modules declare their part of the bridge in their own `shared/` folders, and this module's preload script and `main/bridge.ts` carry it.

## Dependencies

- May import any feature module, to compose it; no module may import this one, which the rule `app-is-the-entry` in `.dependency-cruiser.js` enforces.
- Today it imports Electron, Node.js built-ins, React, react-i18next, zod, and the i18n, workspaces, sessions, approvals, panels, files and toolset modules and the three provider adapters.
- The preload script imports only Electron and `shared/` code, and no other code imports it: the rules `preload-only-to-shared-and-electron` and `nothing-imports-the-preload-script` enforce this.

## Invariants

- The page has no Node.js and its renderer process is sandboxed: `tests/smoke/launch.spec.ts` checks that the page sees neither `require` nor `process`, that macOS reports the renderer process as sandboxed, and that the page holds only the bridge's functions and no Electron objects.
- The main process answers only the app's own page, and only with the calls the bridge declares.
- Only web links leave the app: `shell.openExternal` never receives another scheme.
- The window's page never scrolls: `tests/smoke/sessions.spec.ts` opens a long session, given by the main process in place of a provider's, and checks that the page is no taller than the window and that the wheel moves only the timeline (L-0001).
- Smoke tests run the built app on a throwaway data folder of their own (`tests/smoke/app.ts`), never on the user's.
