## Responsibilities

- `createCodexProvider` (`main/adapter.ts`) implements the sessions module's `Provider` on `codex app-server` (ADR-0003), run from the binary that the pinned `@openai/codex` package brings for macOS on Apple silicon (`main/binary.ts`). Each session has an app-server process of its own, started in the session's folder:
  - Connection (`main/rpc.ts`): JSON-RPC over standard input and output, one message per line. Codex's log output is drained and never kept.
  - Start: `thread/start` with the chosen model, the mode's approval settings and the sandbox level's sandbox; a chosen reasoning effort goes with the first turn.
  - Resume: `thread/resume`, then the thread's turns page by page (`thread/turns/list`), replayed before `replay-finished`.
  - History: the folder's threads, newest first, without subagents' threads (`thread/list`); and a thread's past turns as a resume replays them (`history`), page by page, from a short-lived app-server, which lists a stored thread's turns without loading it (`thread/turns/list`), with the thread's name, the title Codex keeps for it, where it has one (`thread/read`). Such a short-lived app-server, as for the models and the account, is a probe: it answers once its process has exited, and the adapter keeps it from the moment it starts (the sessions module's `Probes`), so that closing the provider, as the app quits, stops one still running and waits for it.
  - Turns: `turn/start` and `turn/interrupt`; a message's images go after its text as data URLs (`image` inputs). A message sent during a turn joins it, with its images, through `turn/steer`, once Codex has said which turn runs; one that Codex refuses, as into a turn that has just ended or that takes none, such as a compaction, starts a turn of its own, at once or once the running turn ends, together with any others waiting. Reasoning summaries follow Codex's own configuration, which a gateway may need without them. A switched model, effort, mode or sandbox level goes with the next turn, which is when Codex takes them: Codex 0.166.0 has no way to change the sandbox of a running turn, in its stable or its experimental API.
  - Modes (ADR-0006): `auto` is on-request approvals, decided by Codex's automatic reviewer, which also decides when a command asks to leave the sandbox; `yolo` is an approval policy of never, in which nothing leaves the sandbox. Neither touches the sandbox. Approvals waiting when the session enters `yolo`, and any that Codex asks for before the next turn, are allowed by the adapter.
  - Sandbox levels: read-only, workspace-write and full access are Codex's `read-only`, `workspace-write` and `danger-full-access` sandboxes, given to the thread when it starts or resumes, whatever the mode. A switched level goes with the next turn as the policy Codex gave the thread for that level, as Codex's own settings shape it (such as `[sandbox_workspace_write]`), or else as Codex's default, in which workspace-write writes in the session's folder and the temporary folders, without network. The session reports the sandbox Codex holds the thread to, which Codex's own settings may decide.
  - Gateways (`main/gateways.ts`): Codex profile files named `<name>.toml` in `$CODEX_HOME/gateways`, or else `~/.codex/gateways`, listed by name. Codex loads profiles only from its home folder, so the adapter reads the selected file when a thread starts or resumes and sends its settings with the thread, its `model_provider` as the thread's provider. A token in the file passes to Codex in memory and is never kept, logged or shown, and Codex's errors are told with the file's strings hidden (ADR-0008). A gateway switch resumes the thread on a new app-server with the other file's settings; asked for during a turn, it waits for the turn's end. When Codex keeps a resumed thread on its earlier provider, the session reports it.
  - Models: `model/list`, without hidden models, asked of a short-lived app-server in a throwaway folder that goes when it is done, or as the app's process exits should the app quit first; a gateway's own model leads the list when Codex does not offer it. The model Codex uses when a thread chooses none is marked as the default (`isDefault`), and each model carries its own default effort (`defaultReasoningEffort`).
  - Toolset (ADR-0012): every session opens the app's toolset, given as `options.toolset`, and starts its app-servers with `-c mcp_servers.3mukon-code.*` settings: the toolset's address; `bearer_token_env_var` naming `TOOLSET_3MUKON_CODE_TOKEN`, which holds the session's credential in the app-server's environment, and which Codex's default shell environment policy keeps out of the commands it runs, since the name contains `TOKEN`; `default_tools_approval_mode = "approve"`, so the toolset's tools run without asking in every mode; and `required`, so no thread starts without the toolset. The toolset has no tools in this version. The access lasts across gateway switches and closes with the session.
- Translation (`main/translate.ts`): agent messages and reasoning summaries stream in as message deltas, each part of a summary a paragraph of its own; a generated image (`imageGeneration`) is an agent message of its own, the images an MCP tool returns show with its call, and the user's images in a thread's history, data URLs as the app sends them, with their message; commands become tool calls named by what Codex made of them (reading, searching or running), with their output streamed; file changes become edits and unified diffs (`main/patch.ts`), built from an added file's content, a deleted file's former content or an update's hunks; the turn plan becomes the task list, where Codex keeps one: its plan tool (`update_plan`) is off unless Codex's own settings turn it on (`tools.update_plan.enabled = true` in its `config.toml`), and the app leaves that as it is; MCP tool calls, web searches and image views become tool calls, a web search by what it did: a search by its first query, with all its queries as its output when it ran several, a page it opened by its address, text it found in a page with the page, and pages it opened without a query, which Codex reports as another action, by their domains, with their titles as its output; a denial by the automatic reviewer shows on the call it denied; turn ends, errors, titles and rerouted models are reported, and the context the thread takes, as its last request's tokens of the model's window (`thread/tokenUsage/updated`).
- Approvals and questions (`main/requests.ts`): command, file change and permission approvals, where "allow for the session" is Codex's own session approval; `request_user_input` becomes a question, answered by question id. Codex's async questions (`request_user_input_async`), which it asks in every mode without waiting for the answer, come as an agent message that carries them and show as a question in its place, answered by message: one choice or a typed answer each, the answer alone for a single question, else each question with its answer under it, going out as the user's next message, into the running turn while one runs; a message of the user's own is taken as the reply, and a thread's history shows the agent's message. MCP elicitations, which only the user's own MCP servers send, are declined, since those servers are not part of this version, and other requests from the app-server are refused.
- Protocol types (`main/protocol/`): generated from the bundled Codex by `scripts/codex-protocol.mjs` (`corepack pnpm run codex:protocol`), which keeps the types the adapter names and the types they import. They are regenerated with each upgrade of `@openai/codex`, never edited by hand, and left out of ESLint.
- The account (`main/account.ts`, ADR-0017): the adapter also implements the accounts module's `AccountSource`, through a running session's app-server on Codex's own sign-in, or else a short-lived one in a throwaway folder: `account/read` for the sign-in, a ChatGPT account being a subscription, Amazon Bedrock or a provider needing no OpenAI sign-in another backend, and any other a key; `account/rateLimits/read`, without the resets' details, for the primary and secondary windows and how many resets the account holds; `account/rateLimitResetCredit/consume`, one attempt with a key of its own, for a reset; `codex login` as the sign-in command. A session on Codex's own sign-in passes on `account/rateLimits/updated` and a turn refused as `unauthorized`; a gateway's account is the gateway's. A failed limits request says why the usage was not read, the sign-in refused or Codex unreachable, and an answer of another shape says so. The answers are checked with zod rather than generated, since the generated account types also describe the sign-ins the app never uses.

## Not responsible for

- Signing in: Codex signs in through its own `codex login`, which the app runs in a terminal, and keeps its credentials itself; this module never reads or passes them (ADR-0008, ADR-0016).
- Codex's own question tool that waits for the answer: Codex offers `request_user_input` only in its plan collaboration mode, which needs its experimental API, and this version does not turn that on; sessions ask through Codex's async one instead (ADR-0012).
- Overriding the automatic reviewer's denials, Codex's command-policy amendments, collaboration modes, reviews, and Codex's own file and command methods.
- Hosting: the main process runs the adapter. electron-builder.yml unpacks the Codex binary, with the tools beside it, beside the app's archive, and `bundledCodexBinary` (`main/binary.ts`) gives its path there in the packaged app.

## Interface

- `createCodexProvider(options)` from `main/adapter.ts`, which returns a `Provider` (DOC-mod-sessions) that is also an `AccountSource` (DOC-mod-accounts). `options.toolset`, the app's toolset (DOC-mod-toolset), is required; `options.gatewaysDir` replaces the gateways folder and `options.startRpc` the app-server, for tests.

## Dependencies

- Uses only the sessions module's interface and model (`src/sessions/main/provider.ts` and `src/sessions/shared/`), the accounts module's interface and model (`src/accounts/main/source.ts` and `src/accounts/shared/`), the `@openai/codex` binary at run time, `zod`, `smol-toml`, `diff` and Node.js built-ins; the toolset reaches it through that interface. The live test also starts the toolset, as the app module does. The rules `providers-only-to-sessions-and-accounts-contracts`, `provider-live-tests-compose-as-the-app` and `providers-not-to-each-other` in `.dependency-cruiser.js` enforce this.
- Only the app module, which hosts providers, may import it.

## Invariants

- Sessions start in `auto` unless the user chose `yolo`; `yolo` is only ever entered by the user's choice.
- A sandbox level's settings never depend on the mode, and switching one never changes the other.
- A gateway file's settings stay in memory only while a thread starts or resumes, and never reach logs, errors or the renderer.
- Every session gets the toolset, and its credential reaches Codex only through the app-server's environment.
- The protocol types match the bundled Codex: `corepack pnpm run codex:protocol` runs after each upgrade.
- The unit tests put a fake app-server in place of Codex (`main/adapter.test.ts`) and run the connection against a stand-in process (`main/rpc.test.ts`). The live test (`main/adapter.live.test.ts`) drives a real session with the real toolset in a throwaway folder on the account's usage, so only `corepack pnpm run test:live` runs it; it checks that Codex's async question shows as a question and that its answer reaches the agent.
