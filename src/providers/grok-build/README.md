## Responsibilities

- `createGrokBuildProvider` (`main/adapter.ts`) implements the sessions module's `Provider` on `grok agent stdio` (ADR-0003), through the stable API of the ACP TypeScript SDK. Each session has a Grok process of its own, started in the session's folder as `grok --no-plan --sandbox <profile> agent --no-leader stdio`, so that no shared leader process serves it:
  - Binary (`main/binary.ts`): the app depends on the pinned `@xai-official/grok-darwin-arm64` package directly, since the `@xai-official/grok` package around it would copy the binary into the user's Grok home from its install script. The package carries the binary compressed; the adapter unpacks it once per version into a folder of the app's own and runs it from there. A folder that is a link, or that anyone but the user can write to, is refused. Each start marks the copy it runs as run, and removes the copies that no build of the app has run for a week, whether of other versions or left partial by an unpacking that did not finish: builds that share the app's data folder, such as a development build beside a packaged app, may each run another version and keep their own copy, while a version no build runs any more goes a week after its last run. A partial copy being written is new and stays.
  - Connection (`main/process.ts`): ACP over standard input and output. Grok's log output is drained and never kept. The app tells Grok that it reads and writes no files and runs no terminals for it, so Grok uses its own tools.
  - Start: `session/new` in the session's folder, with `_meta.askUserQuestion`, which has Grok ask through its own question tool, and the mode's flag; then the model and effort if chosen.
  - Resume: `session/load`, which replays the session's updates before `replay-finished`.
  - History: the folder's sessions from `session/list`, page by page, newest first, asked of a short-lived process at the read-only level. Such a process answers as soon as its exchange ends and then stops on its own: Grok takes about four seconds to exit, which no answer waits for, and leaves nothing in its folder. The adapter keeps each such process, a probe, from the moment it starts, before Grok answers it, until it has exited (the sessions module's `Probes`); closing the provider, as the app quits, stops those still running, one still starting as soon as it starts, and waits for them. A Grok stopped while it is still starting exits at once. A past session's events (`history`) come the same way: Grok replays a session to the process that loads it (`session/load`), and the process sends the session nothing before it stops. The replay leaves out the title Grok keeps for the session, so the history takes it from `session/list`.
  - Tool calls: a call Grok titles `<server>__<tool>` carries that server and tool (`mcp`), the app's own toolset by its own name rather than `sanmukon-code`, and one of the app's tools that Grok titles by its name alone, as its `use_tool` does, is known by the session's registered tools; the arguments of a call through `use_tool` are its `tool_input`.
  - Titles (ADR-0035, ADR-0037): Grok titles its sessions on its own, and the host keeps those titles. For a session Grok leaves untitled, `writeTitle` answers a title's prompt from a new session of a probe in a throwaway folder at the read-only level, with the session's model and effort set through `session/set_config_option`; it takes the agent's message chunks once the prompt ends its turn, fails on any other stop reason or after two minutes, and, since Grok's agent mode keeps its built-in tools, cancels the prompt and fails once the agent starts a tool call. The session is then deleted from Grok's history with the undocumented `_x.ai/session/delete`, which takes `{ sessionId }`. `setTitle` gives a session its title with the undocumented `_x.ai/session/rename`, which takes `{ sessionId, title }`, and reports it.
  - Inbox notices (ADR-0036): a prompt or an interjection carries the notices of new messages as a resource of its own (`app://3mukon-code/inbox`) beside the presentation state's; `deliverContext` prompts with that context alone, reporting no message of the user's; the history gives back such a resource as an `inbox` event.
  - Turns: `session/prompt`, with a message's images after its text as image blocks, which Grok takes (`promptCapabilities.image`), which Grok answers when the turn ends, and `session/cancel`, after which the adapter answers what is still open as cancelled. Grok's stop reasons give the turn's outcome. A message sent during a turn joins it through Grok's interjection (`_x.ai/interject`, `main/turns.ts`), its images as the interjection's content blocks, which Grok delivers at the turn's next safe point, as its own terminal client does. After an interjection without text, Grok's agent sends its client nothing more, though its turn goes on, so images sent alone go with a short text of the app's, `(image attached)` or `(images attached)`, which Grok sees and the session's activity does not show. A message that Grok refuses waits in the adapter and starts the next turn, together with any others, as one prompt: a prompt sent to Grok during a turn would wait in Grok's own queue, which joins the turn only under Grok's `[ui].follow_up_behavior = "steer"` and which Grok holds after a cancel until the next prompt. An interjection that reaches Grok after its turn has ended runs as a prompt of Grok's own, which no prompt request frames: the session follows a prompt that Grok's queue notices (`_x.ai/queue/changed`) say runs while no turn of the session runs, or still runs when a turn's answer comes, until Grok's notice that its turn completed (`turn_completed` in `_x.ai/session_notification`). As Grok retries a request to the model that failed, its notice of its retry state (`retry_state` in `_x.ai/session_notification`, `main/turns.ts`), while that state is `retrying`, becomes `retrying`, with the retry Grok makes, how many it makes at most and its reason, such as `API error (status 500 Internal Server Error): …`; its `exhausted` and `failed` states, as it gives up, add nothing, since the turn's end ends the wait. Checked against Grok 1.0.70 with live turns outside the live test: an interjection of text, one of text with an image and one of an image alone, each delivered to the model, and one sent after its turn.
  - Modes (ADR-0006): `auto` is Grok's auto mode, in which a classifier reviews each action and asks when it will not allow it; `yolo` is its always-approve mode. Grok 1.0.92 takes the mode only as a flag of the session's `session/new`, `session/load` and `session/resume`, `_meta.autoMode` or `_meta.yoloMode`, without which a session runs in Grok's ask mode, and it refuses `session/set_mode` for every mode but its conversation's default and plan. So a switch resumes the running session in its own process with the new mode's flag, which replays nothing and takes effect at once; each of the session's updates still reaches the app once, as checked against Grok 1.0.92 between turns. Approvals waiting when the session enters `yolo` are allowed, and so is one that Grok still asks for in `yolo`, without showing. Grok's own plan mode stays off (`--no-plan`): the app has no plan mode, and Grok asks to leave its plan mode through an undocumented extension request.
  - Sandbox levels: read-only, workspace-write and full access are Grok's `read-only`, `workspace` and `off` profiles, whatever the mode. Grok's `workspace` profile writes in the session's folder, Grok's own home (`~/.grok`) and the temporary folders, and its `read-only` profile in the last two only. Grok applies a profile to its whole process as the process starts, so a switch moves the session to a new process at the new level, which resumes it with `session/resume`, which replays nothing; the mode, model and effort go along. The switch happens at once between turns, and when the turn ends if asked for during one. Should the new process fail, the session goes back to one at its earlier level, settles and publishes that process's model catalog as it does for a successful switch, and then uses those defaults for later model or effort resets.
  - Profiles on resume: Grok's own CLI refuses to resume a session under another profile than the one it was saved with, but in agent mode Grok 1.0.92 loads and resumes a session in a process of any profile, and the process's profile is the one in force. The switch relies on that, and the live test checks it.
  - Models and effort: the models the account can choose, with their effort levels and defaults, come from Grok's `x.ai/models/list`, asked of a short-lived process as for the history, in a throwaway folder that goes when it is done, or as the app's process exits should the app quit first, so listing them starts no session. Grok answers `initialize` at once with the catalog it holds, its cached one while the cache is fresh, or else only its built-in models until its first fetch lands; `x.ai/models/list` waits a bounded time for that first catalog, as `session/new` does, and only where it fails or does not answer within 20 seconds does the list come from `initialize`'s `modelState`. A session takes the same call's catalog once Grok has attached it, and the catalog of each later `x.ai/models/update`, with which Grok announces a changed catalog. The current model is marked as the default, and each model carries its own default effort. Grok takes these defaults from its own settings, whose layers include no project's, so the folder that `listModels` is given goes unused. A session switches its model and effort at once through ACP's configuration options (`session/set_config_option` with `model` and `reasoning_effort`); going back to the default sets the account's starting model, or the model's own default effort. Grok's custom models, each with an endpoint of its own, are among its models; Grok has no gateways, and the adapter refuses one.
- Translation (`main/translate.ts`): ACP's message chunks carry no ids, so the chunks of one role make one message until something else comes between; an image chunk joins its message's images, the agent's thought chunks are its thinking, and the images a tool call shows go with the call. Grok's echo of the user's message stays out of live turns and is kept in replays, and updates of other sessions, such as subagents', stay out. Tool calls keep ACP's kinds and statuses, with the command, the files they name, a file tool's `file_path` included, and the text they print. A completed call's diffs become file changes and unified diffs (`main/patch.ts`), in which a file without a text before, or with an empty one as Grok gives a file it creates, is new. ACP's usage updates become the context the session takes, of its window. The plan becomes the task list; titles, mode updates and the configuration options' model and effort are reported.
- Approvals and questions (`main/requests.ts`): `session/request_permission` becomes an approval with the call's command, files and diff, taken from the call's earlier updates where the request shows less. Grok's "always" answers would outlast the session, so an approval offers allowing once and denying only, and is answered with Grok's once options. Grok's own question tool asks through the `_x.ai/ask_user_question` extension request; every question also takes typed text, as Grok's own question card does, and the answers go back by question text, with the chosen labels and any typed text joined. A question that is declined, that Grok gives up, or that is still open when the turn ends is cancelled.
- The account (`main/account.ts`, ADR-0017): the adapter also implements the accounts module's `AccountSource`, through a running session's process, or else a short-lived one in a throwaway folder, with Grok Build's undocumented extension methods behind its text interface's `/usage`, checked as Grok Build 1.0.92 answers: `x.ai/auth/info` for the sign-in, the token `grok login` stores (`cached_token`) being a subscription, any other method a key and none signed out; `x.ai/billing` for the plan's current period, its span from its type, the share of its included credits used where the plan has them and its end. A failed billing request says why the usage was not read, the sign-in refused or Grok unreachable, and an answer of another shape says so. A prompt refused with ACP's authentication error is passed on. `grok login`, from the unpacked binary, is the sign-in command. Grok offers no reset.

- ACP's HTTP server entry carries no tool-call timeout, so Grok's own limit for a call to the toolset applies: its bundled documentation gives 6,000 seconds, though one older passage there says 60. A call waiting longer for the user's answer to its approval ends at Grok's limit.
- Grok knows the toolset's server as `sanmukon-code`. Grok registers a server's tools only if the server's name starts with a letter or an underscore, and otherwise skips them all, so the adapter gives the leading 3 of the toolset's `3mukon-code` to Grok as san, the Japanese word for three, in the session's server, the allow rules and the titles that route approvals and results; the other providers keep `3mukon-code`.
- The session process receives one native `--allow MCPTool(server__tool)` rule per registered host tool. These name this app's server and each tool exactly, never a bare name or a wildcard across servers. A qualified ACP callback can still go straight to the broker, but a bare title cannot authorize a call: another MCP server may offer the same name. Grok's model reaches MCP tools through `search_tool` and `use_tool`, which take the qualified name; a `use_tool` call under a bare name matches no rule, so Grok asks for it as for any tool without one. The broker independently enforces its sandbox and operation grants.
- Automation results use registered native tool metadata and the outer structured/text envelope; arbitrary model prose and nested page content are never searched for receipts. Grok's native MCP completion omits the title, kind and content, carrying its result as a JSON string at `rawOutput.output.OkayOutput`, or, for a result the server marked `isError`, such as a refusal, at `rawOutput.output.Error` with `is_error`, which Grok reports as failed; the adapter takes the variant `is_error` names and nothing from an output holding another or two. The adapter unwraps it only when `type` is `MCP`, `server_name` is the name given to Grok and `tool_name` matches the registered tool identified by the preceding native updates. A foreign, conflicting or malformed wrapper cannot fall back to another receipt in its outer fields or text content. The existing bounded receipt reader validates the decoded envelope. Grok's `use_tool` dispatcher can change its title to a bare tool name, with `x.ai/tool` identifying only the dispatcher. That name is a candidate for correlation, not approval: the bound host must match the opaque receipt to a retained call's owner, turn, generation and canonical tool name before joining activity or retiring notices. Both name maps are bounded and cleared on reconnect. Grok receives separate embedded-resource context only when advertised. A full prompt response confirms delivery; its interjection's queue acknowledgement does not, so those notices remain pending. Native HTTP/image capability flags are reported separately from optional backend availability.

## Not responsible for

- Signing in: Grok signs in through its own `grok login`, which the app runs in a terminal, and keeps its credentials in its own home; this module never reads or passes them (ADR-0028, ADR-0016).
- Host execution policy: the shared broker authorizes operations independently of Grok's permissions. The adapter passes its bound HTTP toolset on new, load and resume, rotates access on process replacement and forwards registered tool callbacks in both modes. Missing HTTP support is reported without disabling chat. Grok's own question tool remains its own.
- Grok's plan mode, its extension methods beyond the question tool, the interjection and the notices of its queue, turns and retries (such as fork, rewind and compaction), MCP elicitations, and its own MCP servers, hooks and skills, which run as Grok's settings say.
- The environment of an app opened from the Finder: Grok runs with the app's environment, so a variable that a custom model reads its key from reaches Grok only when the app has it.
- Hosting: the main process runs the adapter and gives it the folder for the binary.

## Interface

- `createGrokBuildProvider(options)` from `main/adapter.ts`, which returns a `Provider` (DOC-mod-sessions) that is also an `AccountSource` (DOC-mod-accounts). `options.binaryFolder` is the app's folder for the unpacked binary; `options.startGrok` replaces the process, for tests.

## Dependencies

- Uses only the sessions module's interface and model (`src/sessions/main/provider.ts` and `src/sessions/shared/`), the accounts module's interface and model (`src/accounts/main/source.ts` and `src/accounts/shared/`), the ACP TypeScript SDK `@agentclientprotocol/sdk`, bundled, the `@xai-official/grok-darwin-arm64` binary at run time, `zod`, `diff` and Node.js built-ins. The rules `providers-only-to-sessions-and-accounts-contracts` and `providers-not-to-each-other` in `.dependency-cruiser.js` enforce this.
- Only the app module, which hosts providers, may import it.

## Invariants

- Sessions start in `auto` unless the user chose `yolo`; `yolo` is only ever entered by the user's choice.
- A sandbox level's profile never depends on the mode, and switching one never changes the other; every process runs at an explicit profile, `off` included.
- The binary runs only from a folder of the app's own that only the user can write to.
- The unit tests put a fake Grok, on the ACP SDK's own agent side, in place of the process (`main/adapter.test.ts`). The live test (`main/adapter.live.test.ts`) drives a real session on the account's usage, in a throwaway folder outside the temporary folders, which Grok's read-only profile can write to, so only `corepack pnpm run test:live` runs it. It checks that Grok's question tool asks in `yolo`, that read-only stops a write, and that the session can write once switched to workspace-write.
