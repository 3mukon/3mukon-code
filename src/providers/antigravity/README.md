## Responsibilities

- `createAntigravityProvider` (`main/adapter.ts`) implements the sessions module's `Provider` on `agy acp` (ADR-0040), through the stable API of the ACP TypeScript SDK. Each session has an Antigravity process of its own, started in the session's folder as `agy acp --process-per-session`, with `--sandbox` at read-only and workspace-write: only with `--process-per-session` does Antigravity take the app's toolset over HTTP, and its front process then serves the session from a worker of its own.
  - The CLI (`main/install.ts`, ADR-0039): `antigravityInstall` describes Antigravity's CLI to the installs module: `agy` on the PATH, from 1.5.18 on, whose `--version` prints the bare version. The app's copy is Google's build for macOS on Apple silicon, by `main/pin.json`: the versioned address and the SHA-512 that Google's update manifest gave for it, which `corepack pnpm run providers:pins --antigravity` writes. The binary, `antigravity`, lies at the tarball's root. The app's copy runs with `AGY_CLI_DISABLE_AUTO_UPDATE` set, the binary's own undocumented switch for its updater, which would otherwise replace the copy with a newer build than the pin; the user's `agy` runs as the user keeps it (`launchEnv`). A session takes its binary from `prepare`, which may download the app's copy first; a probe takes the one `current` gives.
  - Connection (`main/process.ts`): ACP over standard input and output. Antigravity's log output is drained and never kept; Antigravity writes its own log in its settings folder, as it does for the user's runs. The app tells Antigravity that it reads and writes no files and runs no terminals for it, so it uses its own tools, and that it shows forms, through which Antigravity's question tool asks. A process asked to stop has its input closed, so that its front process ends its worker, and is ended outright after three seconds.
  - Start: `session/new` in the session's folder, with the toolset as an HTTP MCP server; then the model and thinking level where chosen, and Antigravity's mode behind the app's.
  - Resume: `session/load`, which replays the session's updates; the app reports `replay-finished` once it has answered.
  - History: the sessions from `session/list`, page by page. Antigravity lists every folder's sessions whatever folder it is asked for, each with its own, so the folder's are picked out here; a session's title is its first message until Antigravity gives one of its own. A past session's events come from a short-lived process that loads it: Antigravity replays each user message, each tool call once, complete, each agent message whole, then the context in use and the title. Such processes, the probes, are kept from the moment they start until they have exited (the sessions module's `Probes`); closing the provider, as the app quits, stops those still running and waits for them.
  - Models and thinking levels: the `model` and `thought_level` configuration options. The session's model takes the levels its thinking-level option lists; every other model those its variants name in ACP's list of models, as Antigravity lists `gemini-3.8-flash-low` beside `gemini-3.8-flash`. The model a session starts with is the default, with its level. `listModels` reads them from a new session of a probe in a throwaway folder, which runs no turn and is closed once read. A session switches its model and level at once; a level the new model does not take is left to Antigravity. Antigravity offers the models its sign-in has, third-party ones included, and has no gateways; the adapter refuses one.
  - Turns: `session/prompt`, with the context, the message's text, then its images, which Antigravity takes (`promptCapabilities.image`), and `session/cancel`, after which the adapter answers what is still open as cancelled. A message sent during a turn goes as a prompt of its own, which steers the running turn: Antigravity answers the prompt before at once and goes on under the new one, so the turn ends, once, with the answer to its last prompt. The stop reason gives the turn's outcome. A refusal of the account, such as one for an account Google does not serve, comes as the agent's message in an ordinary turn, and shows as such.
  - Modes (ADR-0006, ADR-0040): in auto, Antigravity's auto mode runs where the session's modes offer it, except at read-only, since it approves edits without asking, as its own description says ("Approve edits and safe commands; ask before irreversible actions"), while Antigravity's file tools are outside its sandbox; elsewhere its default mode runs, which asks before edits and commands. A mode switch applies at once through `session/set_mode`; should Antigravity refuse its auto mode after all, its default mode runs. Plan mode and accept-edits are never set.
  - Sandbox levels (ADR-0040): the terminal sandbox holds for a whole process, so a switch to or from full access moves the session to a new process, which resumes it with `session/resume`, replaying nothing, at once between turns and once the turn ends if asked for during one; the mode, model and level go along. Should the new process fail, the session goes back to one at its earlier level. A switch between read-only and workspace-write changes Antigravity's mode and the adapter's answers alone, at once. In 1.5.18 the sandbox lets a command write in the temporary folders only, not in the session's folder, even one Antigravity trusts (`trustedWorkspaces`), so a command that must write there asks to run outside it.
  - Inbox notices (ADR-0036): a prompt carries the notices of new messages as a resource of its own (`app://3mukon-code/inbox`) beside the presentation state's; `deliverContext` prompts with that context alone, reporting no message of the user's; the history gives back such a resource as an `inbox` event. The notices of the prompt that opens a turn count as taken once Antigravity's first output for the turn comes, which is before ACP answers the prompt at the turn's end, so that they show before what the agent makes of them; a prompt that steers a running turn is taken as it is answered.
- Translation (`main/translate.ts`): ACP's message chunks carry no ids, so the chunks of one role make one message until something else comes between; the agent's thought chunks are its thinking. Tool calls keep ACP's kinds and statuses, with the command of a `run_command` (`CommandLine`), the files they name, and the text they print, after Antigravity's short header of times and exit code. A completed call's diffs become file changes and unified diffs (`main/patch.ts`). Antigravity names a call, beside ACP's fields, such as `run_command` or `mcp_<server>_<tool>`; a call of the app's own tools shows as that tool, without the `toolSummary` Antigravity adds to every tool's input, and other servers' calls keep Antigravity's title, since a server's name and its tool's cannot be told apart where either holds an underscore. ACP's usage updates become the context the session takes, of its window; titles and the configuration options' model and level are reported; Antigravity's own mode updates stay out, since the session's mode is the app's. Antigravity sends no plan, so a session has no task list.
- Approvals and questions (`main/requests.ts`): `session/request_permission` becomes an approval with the call's command, files and diff, taken from the call's earlier updates where the request shows less, answered with Antigravity's allow-once or deny-once options, the only answers it offers. A request beyond the session's level (ADR-0040) is asked with denial preselected in auto, and denied in yolo, which allows every other request: at read-only an edit, or a command whose input asks to leave the sandbox (`BypassSandbox`); at workspace-write such a command, or an edit of a file outside the session's folder and the temporary folders, or one that names no file. A call of one of the session's registered tools in the app's server is allowed without asking, since the broker authorizes it. Antigravity 1.5.18 ends its turn without a reply once a request is denied. Antigravity's question tool asks through ACP's form elicitation (`elicitation/create`): one property per question, its choices as consts titled with their labels, and a property named after it with `_other` for typed text, which the question then takes. The answer gives each question's chosen values, as a list for a question of several choices, and the typed text; a declined form is declined, and one still open when the turn ends is cancelled, as is any other kind of elicitation.
- The account (`main/account.ts`, ADR-0017): the adapter also implements the accounts module's `AccountSource`, through a short-lived process in a throwaway folder. Antigravity is signed out where it refuses `session/list` with ACP's authentication error (-32000, "Authentication required"), and otherwise signed in: with a subscription where `authenticate` with its `terminal-login` method, which takes up the sign-in Antigravity holds, reports a tier (`_meta.antigravity.tier`), and else through another backend, such as a key or a cloud project set in Antigravity's own settings. Antigravity offers no program its usage limits, so a subscription's show as unavailable (`unoffered`). A prompt refused with the authentication error is passed on as signed out. The sign-in command is the binary's `acp --login`, Antigravity's sign-in in a terminal by a pasted code.

## Not responsible for

- Signing in: Antigravity signs in through its own `agy acp --login`, which the app runs in a terminal, and keeps its credentials in the macOS keychain; this module never reads or passes them (ADR-0016). Keys and cloud projects are set up in Antigravity's own settings, which the app never changes.
- Host execution policy: the shared broker authorizes operations independently of Antigravity's permissions. Antigravity reports a toolset call's completion without its result, so no receipt links the call to the broker's record of it, and the presentation notices of a turn settle with its prompt's answer.
- Antigravity's plan mode, its slash commands, its subagents and swarms, its own MCP servers, hooks, skills and plugins, which run as its settings say, and its settings and trusted folders.
- Titles of the app's own: Antigravity gives every session a title, its first message until its own, which the host keeps (ADR-0037); there is no call to rename a session.
- Hosting: the main process runs the adapter and gives it Antigravity's install.

## Interface

- `createAntigravityProvider(options)` from `main/adapter.ts`, which returns a `Provider` (DOC-mod-sessions) that is also an `AccountSource` (DOC-mod-accounts). `options.install` gives where Antigravity's processes come from (DOC-mod-installs); `options.startAgy` replaces the process, for tests. `launchEnv` gives a binary's variables.
- `antigravityInstall` from `main/install.ts`, for the app module.

## Dependencies

- Uses only the sessions module's interface and model (`src/sessions/main/provider.ts` and `src/sessions/shared/`), the accounts module's interface and model (`src/accounts/main/source.ts` and `src/accounts/shared/`), the installs module's interface (`src/installs/main/install.ts`), the ACP TypeScript SDK `@agentclientprotocol/sdk`, bundled, Antigravity's binary at run time, `diff` and Node.js built-ins. The rules `providers-only-to-sessions-and-accounts-contracts` and `providers-not-to-each-other` in `.dependency-cruiser.js` enforce this, which is why the module keeps translation and diff helpers of its own beside Grok Build's.
- Only the app module, which hosts providers, may import it.

## Invariants

- Sessions start in `auto` unless the user chose `yolo`; `yolo` is only ever entered by the user's choice.
- The process's terminal sandbox follows the level alone; Antigravity's auto mode never runs at read-only; no request beyond the level is allowed without the user. The adapter never sets `--dangerously-skip-permissions` or plan mode.
- The app's copy runs only from a folder of the app's own that only the user can write to (DOC-mod-installs), and with its updater off.
- The unit tests put a fake Antigravity, on the ACP SDK's own agent side, in place of the process (`main/adapter.test.ts`), beside tests of the translation and the requests. The smoke and packaged tests have no copy of Antigravity, which has no package, so it shows there as not installed and never runs (L-0007). The live test (`main/adapter.live.test.ts`) drives a real session on the account's quota, on Google's pinned build, which it downloads once per version into node_modules' cache, in a throwaway folder outside the temporary folders, which the terminal sandbox lets commands write in; only `corepack pnpm run test:live` runs it. It checks that the question tool asks in yolo, that read-only refuses an edit in yolo, that workspace-write lets an allowed edit through, and that a switch to full access resumes the session with its conversation in a new process.
