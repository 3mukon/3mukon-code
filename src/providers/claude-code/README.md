## Responsibilities

- `createClaudeCodeProvider` (`main/adapter.ts`) implements the sessions module's `Provider` with `@anthropic-ai/claude-agent-sdk`, which runs the Claude Code binary it brings along (`@anthropic-ai/claude-agent-sdk-darwin-arm64`), from the path `bundledClaudeBinary` (`main/binary.ts`) gives every session and probe: in the packaged app the binary lies beside the app's archive, where macOS can run it, while the SDK would look for it inside:
  - Start: a streaming query under a new session id, in the chosen permission mode (`auto` unless the user chose `yolo`) and on the chosen sandbox level (`workspace-write` unless the user chose another), with Claude Code's own system prompt and with its settings and CLAUDE.md files loaded as in the CLI. A chosen model and reasoning effort go in as the query's `model` and `effort`. Text and thinking arrive as they are written (partial messages); Claude Code shows thinking as summaries (`--thinking-display summarized`, through `extraArgs`), which recent models leave out unless asked for and which it drops itself where the API refuses them. A message's images go before its text as base64 image blocks.
  - Messages during a turn: a message sent while a turn runs goes into the query's input, with its images, from which Claude Code takes it into the running turn between tool calls, or else runs it as the next turn; a result whose `queued_turn_count` is above 0 ends the turn and starts that next one, before which a gateway asked for meanwhile does not switch.
  - Resume: replays the session's transcript (`getSessionMessages`), then continues the session (`resume`).
  - History: the folder's past sessions (`listSessions`), each titled by the title Claude Code keeps or else its first prompt, and a past session's events as a resume replays them, read from its transcript (`getSessionMessages`) without starting Claude Code (`history`), with that title where Claude Code keeps one.
  - Tool calls: a call of an MCP tool, which Claude Code names `mcp__<server>__<tool>`, carries that server and tool (`mcp`); a subagent (`Agent`) is titled by the few words of its task, `Skill` by the skill, `ToolSearch` and `WebSearch` by the query, `Monitor` by its description, `ReadMcpResource` by its address and `ListMcpResources` by its server; any other tool without a file, command or pattern to name it by its name in words, such as Enter worktree.
  - Titles (ADR-0035, ADR-0037): Claude Code titles a session on its own from its first prompt, an AI title that the SDK's `getSessionInfo` reports as the session's `customTitle` where the user gave none, which the adapter reports after the turn as the user's would be and the host keeps. For a session Claude Code leaves untitled, `writeTitle` answers a title's prompt from a Claude Code of its own in a throwaway folder, started as the models' probe is, through the gateway's file or else the user's own settings with their hooks off, with the session's model and effort, a system prompt of the app's own in place of Claude Code's, no tools (`tools: []`), no MCP servers (`strictMcpConfig`), one turn and no transcript kept (`persistSession: false`); it takes the result's text, fails with the result's errors, and fails after two minutes. `setTitle` gives the session the title as its custom title with `renameSession`, which Claude Code keeps in its transcript, and reports it.
  - Inbox notices (ADR-0036): a message's host context goes as documents before its content, the presentation state's and the notices of new messages' (`App inbox`), their delivery accepted once Claude Code takes the message; `deliverContext` starts a turn with those documents alone, reporting no message of the user's; the history gives back a document of notices as an `inbox` event.
  - Modes (ADR-0006): `auto` is Claude Code's auto mode, in which its classifier approves or denies each action and asks through `canUseTool` only when it cannot decide; `yolo` is `bypassPermissions`. Every session starts with skipping permissions allowed, so that it can switch to `yolo` without a restart.
  - Gateways (`main/gateways.ts`): Claude Code settings files named `<name>.json` in Claude Code's gateways folder, `$CLAUDE_CONFIG_DIR/gateways` or else `~/.claude/gateways`, listed by name. A session's gateway file goes to Claude Code by its path, as the query's `settings`; the app never opens it (ADR-0028).
  - Sandbox levels (`main/sandbox.ts`): each level is a set of flag settings that `applyFlagSettings` puts in force, the same in every mode. Workspace-write turns Claude Code's sandbox on with the session's folder and the temporary folders (the user's own and `/tmp`, by their real paths) as the only places commands write; a command that cannot run in the sandbox may ask to run outside it (`allowUnsandboxedCommands`), and the mode decides that request as any other: in `auto` Claude Code's classifier, or the user when it cannot decide; in `yolo` it is allowed without asking. Read-only turns the sandbox on with no folder to write in, also denies writes to the session's folder, allows no command outside the sandbox, and denies the file-editing tools (Edit, Write, NotebookEdit) through deny rules, which hold in `bypassPermissions`. Full access turns the sandbox off. Sandboxed commands run without being asked about (`autoAllowBashIfSandboxed`), and a sandbox that cannot start stops the session (`failIfUnavailable`). The level goes in right after the process starts, before any message, because the SDK refuses its own `sandbox` option beside a gateway's settings file. It owns the flag layer's `sandbox` settings, over any in a gateway's file; read-only also owns its `permissions`, which leaving read-only clears.
  - Switching: `setModel()` and `applyFlagSettings({ effortLevel })` change the model and the reasoning effort in the running process, and `applyFlagSettings` the sandbox level, at once, during a turn too. A gateway switch ends the process between turns and continues the session in a new one that reads the other file (`resume`), so the session keeps its id and its history; asked for during a turn, it waits for the turn's end. The mode, the model, the effort and the sandbox level carry over to the new process: a switch already sent to the old process finishes there first, for 10 seconds at most, and a switch asked for while a gateway switch is under way waits for it.
  - Models: a session's models come from Claude Code's initialization, when it starts and after each gateway switch. Before a session exists, `listModels` asks a Claude Code that gets no message, so nothing is recorded, with its auto-memory off (`CLAUDE_CODE_DISABLE_AUTO_MEMORY`), without which it leaves an empty memory folder for each probe in `~/.claude/projects`, in a throwaway folder that goes when it is done, or as the app's process exits should the app quit first: through a gateway it reads only the gateway's file, and otherwise the user's own settings with their hooks off (`disableAllHooks`); it never reads a project's settings, whose hooks and servers could run from a folder no one trusted yet, so the folder that `listModels` is given goes unused, and a project's own model shows once a session there runs. Hooks in a gateway's file, and managed policy hooks, still run. The app opens none of these files itself (invariant 9, ADR-0028). A probe answers in about a second and a quarter, nearly all of it spent on Claude Code's own requests to its service before it answers; with Claude Code's nonessential traffic off it answers in a third of the time but lists fewer models, so the probe leaves that traffic on. A probe that has not started within 30 seconds is closed, and its list fails. A probe answers without waiting for its process to exit, which takes Claude Code about two seconds once the probe is closed and during which it writes its settings file. So the adapter spawns the process itself, through the SDK's `spawnClaudeCodeProcess` and as the SDK would but without Claude Code's error output, to know when it has exited, and keeps the probe until then (the sessions module's `Probes`); closing the provider, as the app quits, stops the probes still running and waits for them.
  - Defaults: the model a session uses when it chooses none is the one Claude Code's own count of the context names (`getContextUsage` in its summary form, which asks the API nothing), and its row is marked as the default; Claude Code's own Default row, which stands for it, goes unless no other row is that model. A count that has not come within 5 seconds is left out, and Claude Code's own Default row then stays marked. Claude Code does not tell an SDK host which effort a session uses: the init frame of each turn leaves it out, and only `get_settings` names it, beside the raw contents of every settings source, which the app does not ask for (invariant 9). So no row carries a default effort.
  - Context and title: after the initialization and after each turn, the adapter reports how many tokens of the context window the conversation takes, from the same count when it comes within 5 seconds, and the title Claude Code keeps for the session (`getSessionInfo`), where it keeps one: the one the user gave it or the one Claude Code wrote itself. Its summary is not taken, since without such a title it is the latest prompt, which would retitle the session with every message; the sessions module's stand-in, the first message, shows instead.
- Translation (`main/translate.ts`): assistant text and thinking stream in as message deltas, and the complete message that follows adds only its tool calls; the image blocks a tool result holds, such as an image file Read returns, show with its call, and those of a user message in a transcript with that message; tool calls become tool events in ACP's tool kinds; TodoWrite, TaskCreate and TaskUpdate become the task list, where the session has these tools: Claude Code offers them by default only to its older models, Opus up to 4.7, Sonnet up to 4.6, Haiku 4.5 and Claude 3, and to the others when its own settings turn them on (`"env": { "CLAUDE_CODE_ENABLE_TODO_TOOLS": "1" }` in its `settings.json`, which every session reads, with a gateway too). The app leaves Claude Code's default as it is (ADR-0020), so a session on a newer model shows no task list unless the user has turned them on; Edit and Write become file changes, with unified diffs from the edit tools' structured patches, or rebuilt from an edit's strings in a transcript; each turn's init message gives the mode, while the session's model stays the one it chose, which its list knows: the init message names the model as Claude Code resolved it, such as `claude-opus-5-5` for `opus`; results end turns. An error that Claude Code gives instead of an answer, such as a missing sign-in, is reported once, with the turn that fails. Each `api_retry` message, which Claude Code sends as it retries a request to the model that failed, becomes `retrying`: the retry it makes and how many it makes at most, and as the reason the HTTP status and Claude Code's kind of error, such as `529 overloaded`, with spaces for its underscores; a connection that failed has no status, and an error of the `unknown` kind leaves the status alone.
- Approvals and questions (`main/requests.ts`): every `canUseTool` call becomes an approval, or a question for AskUserQuestion; ExitPlanMode, which ends a plan mode that Claude entered by itself, becomes a plan approval, after which the session returns to its own mode. A denial can carry the user's message, which Claude Code gives the model as the reason (`denialMessage`). "Allow for the session" adds Claude Code's suggested rules for the session only, and is offered only when Claude Code suggests rules that may be kept. Answers to questions go back in the tool's input, keyed by question text. Questions reach the user in `yolo` too: Claude Code sends AskUserQuestion to `canUseTool` even in `bypassPermissions`, although the SDK warns that `canUseTool` is not invoked there; the live test checks it.
- Paths in tool calls, approvals and file changes are relative to the session's folder when they lie inside it.
- The account (`main/account.ts`, ADR-0017): the adapter also implements the accounts module's `AccountSource`. The sign-in comes from `claude auth status --json`, run from the SDK's own Claude Code binary for macOS on Apple silicon and kept as a probe, since the command can write Claude Code's settings file: another backend when its API provider is not Anthropic's own, a subscription when it names one, otherwise a key. A subscription's windows come from the SDK's experimental usage call with `skipBehaviors`, through a running session's query on Claude Code's own sign-in, or else a probe that initializes like the models' probe and is closed; it may answer without windows, as when the usage endpoint refuses the sign-in Claude Code holds, and the read then says that the sign-in could not fetch them, or, when Claude Code could not be asked, that it could not. A session on Claude Code's own sign-in passes on each `rate_limit_event`, its use a fraction and its reset in seconds, and an assistant message whose error is `authentication_failed`. `claude auth login` is the sign-in command.

- Automation results use only registered native tool metadata and the outer structured/text envelope; arbitrary model prose and nested page content are never searched for receipts. The bound host validates owner, turn, generation and canonical tool name before joining activity. Claude receives presentation context in a separate document block, with the original user text untouched, and confirms it only on its native user-message echo. Its SDK exposes no model image-input flag. Every Claude model takes images, so the adapter reports image input as supported while the model Claude Code names, as it starts and at each turn's first message, is a Claude model and no gateway is set. Otherwise it stays unknown, and the broker refuses tools that need images.

## Not responsible for

- Signing in: Claude Code signs in through its own `claude auth login`, which the app runs in a terminal, or `/login`, and keeps its credentials itself; this module never reads or passes them (ADR-0028, ADR-0016). Without a sign-in, a turn fails with Claude Code's own message.
- Host execution policy: the shared broker authorizes operations independently of Claude Code's permissions. The adapter connects its bound HTTP toolset through SDK MCP configuration, with the toolset's `callTimeoutMs` as the server's `timeout`, which overrides an `MCP_TOOL_TIMEOUT` the user's environment may set, forwards only registered native tool names without an extra approval, and rotates access when replacing the process. AskUserQuestion remains Claude Code's own.
- Subagents' activity and Claude Code's background tasks: not shown in this version.
- Hosting: the main process runs the adapter. A packaged app opened from the Finder takes the login shell's PATH as it starts (ADR-0019), which Claude Code's commands need; electron-builder.yml unpacks the binary beside the app's archive.

## Interface

- `createClaudeCodeProvider(options)` from `main/adapter.ts`, which returns a `Provider` (DOC-mod-sessions) that is also an `AccountSource` (DOC-mod-accounts); `options.gatewaysDir` replaces the gateways folder, for tests.

## Dependencies

- Uses only the sessions module's interface and model (`src/sessions/main/provider.ts` and `src/sessions/shared/`), the accounts module's interface and model (`src/accounts/main/source.ts` and `src/accounts/shared/`), the Claude Agent SDK, `zod`, `diff` and Node.js built-ins. The rules `providers-only-to-sessions-and-accounts-contracts` and `providers-not-to-each-other` in `.dependency-cruiser.js` enforce this.
- Only the app module, which hosts providers, may import it.

## Invariants

- Sessions start in `auto` unless the user chose `yolo`; `yolo` is only ever entered by the user's choice.
- A sandbox level's settings never depend on the mode, and switching one never changes the other.
- Gateway files are listed and passed by path, never opened.
- The unit tests of the adapter (`main/adapter.test.ts`) put a fake process in place of the SDK's `query`. The live test (`main/adapter.live.test.ts`) drives a real session in a throwaway folder, with a throwaway gateways folder, and checks that read-only stops a shell write and that leaving it lets the Write tool work again. It needs Claude Code signed in and uses a little of the account's usage, so only `corepack pnpm run test:live` runs it, never the check command.
- A smoke test (`tests/smoke/retrying.spec.ts`) runs the bundled Claude Code in the built app, on a throwaway data folder, against a local service that fails every request to the model with an error 500, and finds each retry under Working, with its count and reason, until the turn ends; it needs no sign-in and asks no provider's service, and gives the app a login's environment alone.
