## Responsibilities

- The provider interface (`main/provider.ts`), which each adapter under `src/providers/` implements: `Provider` starts and resumes sessions, with a gateway, a model, a reasoning effort and a sandbox level when chosen, reads a past session's history without resuming it, and lists a folder's past sessions, the gateways set up in the provider's own settings and the models a session could use, and as the app quits ends the processes it runs outside its sessions and waits for them (`close`); `ProviderSession` sends the user's messages, with their images, interrupts the running turn, answers approvals and questions, switches the permission mode, the model, the reasoning effort, the sandbox level and the gateway, gives the session a title in the provider's own store where the provider keeps titles (`setTitle`), starts a turn of the app's own with the host context alone (`deliverContext`), and closes the session; `Provider.writeTitle` answers a title's prompt in a request of its own (ADR-0035). Every provider offers the same two permission modes, `auto` and `yolo`, and sessions start in `auto` (ADR-0006). Every provider also offers the same three sandbox levels on its own sandbox, set independently of the mode: `read-only`, `workspace-write`, in which the agent writes only in the session's folder and in temporary folders, and `full-access`, without a sandbox; sessions start in `workspace-write`.
- Probes (`main/provider.ts`, beside the `close` they serve): `Probes`, where an adapter keeps its probes, the processes it starts outside its sessions, such as those that list its models or read its history or account, each from the moment it starts until it has exited, whoever stopped it. Closing it, as the provider closes, starts no more probes, stops those running and resolves once every one has exited, one still starting included, which is stopped as soon as it starts.
- The event model (`shared/events.ts`): the `SessionEvent` union a session reports (turns, and the retries of a request to the model that failed, which the provider makes while a turn waits; streamed messages, with their images; tool calls, in the Agent Client Protocol's tool kinds and statuses, with the images they return, and for a call of an MCP tool its server and tool in terms every provider shares (`McpCall` in `shared/tools.ts`); the agent's task list; file changes as unified diffs; approvals and questions and their resolution; title, mode, the session's gateway, model, reasoning effort and sandbox level, the models it can switch to, the end of a replay, how much of the context window the conversation takes, errors, closing; the notices of new messages from other sessions the agent was told of (`inbox`, ADR-0036), which the host reports as it gives them and the providers' histories give back; and two of the host's own, which no provider sends: the history it read for a session that is not running, and that session's resumption), together with the requests, answers, history entries, permission modes, sandbox levels and model options, which mark the model a session uses when it chooses none and each model's own default effort. An image (`MessageImage`) is its media type and its bytes in base64; `shared/images.ts` holds what a message can carry to every provider, as Claude's API, the strictest, takes it: PNG, JPEG, GIF or WebP, at most 10 images, each at most 2,000 px on its long edge and 5 MB in base64, and tells an image's type from its first bytes.
- Automation contracts (`shared/automation.ts`, ADR-0023): serializable target/observation facts, operation grants and end records, outcomes with typed refusal details, browser/computer/panel call records and receipts, versioned presentation summaries/latest-state notices, cached availability and setup data. Call records retain approval answers and incident times, with frame metadata whose bytes are fetched separately; target summaries name bounded icons by ID. `AutomationLiveState` excludes history, which full snapshots add and call/grant/notice events maintain. `shared/automation-state.ts` folds numbered events without recopying unchanged history, asking for a snapshot after an epoch change or sequence gap. Neither implements authority.
- The toolset's main contract (`main/provider.ts`): app composition supplies `SessionAutomationHost` to the host, which binds an app owner and policy before a provider receives its native ID. `StartOptions.toolset` is the already-bound factory; its access has a separate revocable generation. `SessionAutomation` receives turn, Stop, policy, disconnect and close events without sessions importing the toolset, and reports since when an operation's approval has waited for the user (`onWaiting`). `Toolset.callTimeoutMs` says how long a provider waits on one of the toolset's calls, where its MCP client lets the app say. `prepareSend` supplies separate `HostTurnContext`; only an adapter declaring `supportsHostContext` receives it and `HostContextDelivery` callbacks. Native confirmation, not the return from a locally queued `send`, accepts delivery. Failed sends or older adapters retain notices, and user text remains unchanged. A failure to prepare this supplemental context does not prevent a user message or by-message question answer from reaching the provider. Shared context selection coalesces queued notices at their latest version within the complete UTF-8 block budget; delivery callbacks can acknowledge that exact subset. `HostTurnContext.inboxNotices` carries the notices of new messages, in a block of their own (`shared/inbox.ts`). `SessionCoordinator`, with `CoordinatedSession`, `ChildRequest` and `InboxEntry`, is what the toolset's session tools reach of the sessions (ADR-0036), called with the calling session's own id from its bound access.
- The session state (`shared/session-state.ts`): `applyEvent` folds a session's events into what the UI shows, a timeline in the order things first happened, in which each tool call holds the files it changed, and the current task list; the requests left open at a turn's end are cancelled, but for questions answered by message (`byMessage`), which wait until the session closes; a session's history folds at once, as the session ended, with no turn running and no request waiting, and the state says while it is still to be read and when it could not be; a resumed session runs again with what it showed. While the provider retries a request to the model that failed, the state holds the retry it makes, of how many at most and why (`retrying`), counting itself the retries of a provider that does not count them, until the agent goes on, with output, an approval or a question, or the turn or the session ends; the user's own message, sent during the turn, leaves it. `sessionStatus` derives running, waiting, idle or closed, and `openRequests` lists the approvals and questions still waiting, oldest first.
- Titles (`main/titles.ts`, ADR-0035): when a session has run for a while (`ranAWhile`: its turns have run a minute in all, or three have ended), the prompt its title is written from (`titlePrompt`: instructions and the conversation so far, without the agent's thinking, the first messages and the latest where it is long), and a reply as a title (`cleanTitle`: its first line without quotation marks, emphasis, heading marks, a label or a full stop, within 60 characters).
- Inboxes (`main/inbox.ts`, ADR-0036): `SessionInboxes`, every session's messages, each with its sender, as the app's id and the title it had, summary, body, when it was sent and, once they happen, when its agent was told of it and when it read the body; an inbox keeps its newest 500 messages, those read leaving first, the untold ones come out the oldest first, 20 at a time, and a session that leaves the lists takes its inbox with it, the messages it sent staying with their receivers. `inboxStorage` keeps them in `session-inbox.json` in the app's data, readable by the user alone, an entry of another shape left out; `memoryInboxStorage` keeps them in memory, for tests. `shared/inbox.ts` holds a message's and an inbox's bounds, a notice's shape and the block the notices travel in (`inboxContext`), which `inboxNoticesOf` reads back from a history.
- The host (`main/host.ts`): `SessionHost` runs the sessions started in the app in the main process, through the providers the app module hands it. It allocates the app owner and binds its automation scope before starting the provider in a folder, folds the session's events into its state from the first, and lists it once the provider has started it, or, for one started with a message, as a page starts it, once that message is in it, so that its row shows the message and the running turn from the first rather than its provider's name and idle for a moment; a message that fails to go leaves the session listed. A running session whose model takes a reasoning effort but which has none, whose provider names no default for the model, as Claude Code names none, gets the starting effort (`effortToSet`), once for each model and effort, so that what it runs with is known. It passes messages, stops, answers to approvals and questions, which it then records in the session's state without a question's typed answers to secrets (`request-answered`), and switches to the session, offers its providers, their gateways and their models, found for each provider, gateway and folder and kept, a page before its first message getting them fresh, as a list found within the last 15 seconds or a new one, one listing at a time for each (a list that fails, or that the provider has not found within a minute, leaves the one kept and is asked for again next time), and gives each session's state as a snapshot counted in events. Until the provider titles a session, its first message, on one line and shortened, stands in for the title. A title the provider reports stands, its own, as Claude Code and Grok Build title their sessions from the first prompt, the user's, or the app's as the provider took it (ADR-0037). Once a session has run for a while without one, as every Codex session does, at a turn's end, the host asks its provider for a title (`writeTitle`) with the session's gateway, the model it runs and that model's low effort (`titleEffort` in `shared/efforts.ts`), beside the session; the title replaces the first message, is kept with the session and given to the provider (`setTitle`), a request that fails is tried again at the next turn's end, three times at most in a run, and a title that comes once the provider has titled the session is dropped (ADR-0035). The host also coordinates sessions (ADR-0036, `coordinator()`): it lists the Sessions list's sessions for an agent; lists for an agent that may start children each provider's models as a child would get them, its own provider's through its gateway and the others' through their own configurations, for its folder, a list found within the last 15 seconds or a new one, or why a provider could not list them (`providers`, ADR-0041); starts a child of a running session that is not a child itself, in its folder, in auto, at its sandbox level or a narrower one, with its provider, gateway, model and effort unless the agent names others, at most eight of a parent's children running at once, the child's first message its task and a title its parent gives it standing, after refusing a model the agent names that the child's provider does not list, with its models and the providers that offer the one asked for, or an effort the agent names that the child's model does not take, with the levels it takes, unless that provider's list cannot be had or holds no model (ADR-0041); ends a child for its parent, or a child for itself a moment after its call returns, which closes it and leaves it listed; puts a message in another listed session's inbox; and gives an agent its inbox and a message's body, which marks it read. It tells a session of its new messages, by their summaries, with the result of its next call to the app's tools, beside the user's next message, or, while the session is idle, with no request waiting on the user and no first message on its way, in a turn of its own (`deliverContext`), as a message comes and as a turn ends with messages untold, and shows each notice in the session's activity once the provider has taken it. `list` gives what the window's lists show (`SessionList`): the Sessions list, the sessions that are not archived, the most recently active first, a session moving up as the user sends it a message and as a turn of it ends, which holds those the records keep and any that is open, so that beyond the sessions open it never holds more than 1,000; how many sessions are archived, the archived sessions themselves coming only when asked for (`archived`), as the archived list opens; and the sessions whose pages the window has shown in this run, as it asked for their snapshots, that the Sessions list does not hold, archived ones and those the records no longer keep, so that their panels keep what they show. Listeners hear whenever any of that changes, a change to an archived session the window has not shown changing nothing; event listeners hear every event, numbered within its session as the snapshots count them. Every session it starts stays in the records, while they keep it, with the title the list shows, the title written for it, its parent for a child, its latest activity, whether it is archived, how much of its context window it took when the provider last counted it, and the settings it has, its permission mode among them, saved as they change; a session of an earlier run shows that context until it runs again, since only the provider's process counts it; the sessions of earlier runs come back from the records, and sessions started in a provider's own tools are never listed. A session that is not running, one of an earlier run or one whose provider stopped, is listed as closed. The first snapshot of one of an earlier run has its history read from its provider without resuming it (`history`), the settings the history reports left out for those the app kept, and the history follows as one event, or a failure with none; `preload` begins that read ahead of the first snapshot, without showing the session, so that its page has the history as it opens. `resume` resumes a session that is not running under the same id, with the settings its page shows, yolo too, since the user chose it for the session (ADR-0006), a gateway no longer set up giving way to the provider's own configuration with its default model and effort; it reads the history first where it has not been read, so that the provider's replay is not shown twice, or else takes the replay as the history, and a session that cannot be resumed stays as it was. A message sent to a session returns it to the Sessions list when it was archived. `archive` moves a session to the archived list and `unarchive` back; `remove` takes it off the lists and out of the records, with its inbox, leaving its provider's history as it is, and the change that drops it from the lists names it (`removedId` on `SessionListChange`) ahead of the session's closing; both close a session while it is open, and each does the same to the session's children. `showMenu` offers a session's menu through the window's (`SessionsMenuUi`), and asks first before it archives a session that is working, or one with a child that is, which stops them, and before it removes one. `closeAll` closes every open session as the app quits, and waits for each to end, as its provider reports a moment later, and for the texts their ends keep to be written. `act` does what a session's menu would without the menu, asking first where the menu asks, for an archived session's row. The host keeps the text of each session's messages, the user's and the agent's, through `SessionTexts` storage (`main/texts.ts`), as its history is read, as a turn of it ends and as it closes, and forgets a removed session's (ADR-0014); `search` finds the sessions of the Sessions list, or of the archived list, whose title and conversation hold every word of a query, whatever its case, a session read in this run as its state is now and others as their kept text, each with the passage of its conversation where the first word it holds appears, and says how many of them have no text yet; `catchUp`, which the app module starts shortly after the window opens, reads one at a time, the most recently active first, the history of each session without a text, keeping its text alone and never resuming it, skips a session read otherwise meanwhile, leaves one whose history cannot be read for the next run, deletes the texts of sessions the app no longer has, and stops as the app quits.
- Confirmations, menus and images (`main/native.ts`): `windowSessionsUi` asks, through the window's prompts (the ui module's `Prompts`, which the window draws in the app's own look, ADR-0013) and in the main process's language, before a session runs in yolo, before a session that is working is archived and before a session leaves the lists, Cancel being the default answer each time; offers the same way a session's menu, Archive, or Unarchive for an archived session, and Remove from List, and an image's menu, Copy Image and Save Image As…, at the pointer; and saves an image where the user chooses in macOS's save panel, as a sheet, Downloads at first. `copyText` and `copyImage` put a message's text, or a PNG image, on the clipboard.
- Day folders (`main/folders.ts`): where a session page opens while no workspace has been added, a folder of the day's date in the day root, `~/3mukon-code`, such as `~/3mukon-code/2026-10-28`, made only when a session starts there, so that a page closed without a message leaves nothing behind. `shared/folders.ts` tells a day folder from any other, in both processes.
- Tools (`shared/tools.ts`): the app's toolset's name (`TOOLSET_NAME`), which the toolset serves under and the adapters and the activity know it by; `mcpCall` and `appCall`, a call of an MCP tool as an adapter reports it, which for one of the app's own tools carries, from its arguments, the words that fit it (`action`, such as reading the inbox rather than one message) and what it acts on in a few words (`subject`: a message's summary, a child's title or the first line of its task, a presentation's title, a page's address), and for an action of the app's browser or computer tools, whether it clicks (`clicks`); and `toolWords`, a tool's name in words, such as Enter plan mode for EnterPlanMode.
- Efforts (`shared/efforts.ts`): `startingEffort`, the effort a session starts with unless the user chooses another, `effortInUse`, the effort a session runs with at the effort it is set to, `effortToSet`, the starting effort where a running session's effort is unknown, and `modelInUse`, the model a session runs, for both processes.
- Remembered settings (`main/choices.ts`): `RememberedChoices`, the settings sessions last used, the provider, gateway, model, reasoning effort and sandbox level: each folder's, by the folder's path, for the 200 folders last used, and one set that all the day folders share, kept in `session-choices.json` in the app's data (`choiceStorage`, readable by the user alone). The permission mode is not among them, so that yolo is entered only on the user's choice (ADR-0006). The window gets them for the providers the app offers.
- Records (`main/records.ts`): `SessionRecords`, the sessions the app started, every archived one and of the others the 1,000 active last: each one's id, provider, the provider's id for it, folder, the title the list last showed, the title written for it (ADR-0035), its parent for a child (ADR-0036), its latest activity, whether it is archived, the context it last took and the settings it last had, its permission mode among them, kept in `sessions.json` in the app's data (`recordStorage`, readable by the user alone), so that later runs list them, show their history and resume them as they were; a session removed from the lists leaves them.
- Session texts (`main/texts.ts`): `textStorage` keeps each session's text in `session-texts/<id>.txt` in the app's data, the folder and its files readable by the user alone, each written whole to a file of its own first, one session's texts one at a time, a text that a later one replaces before its turn never being written, what an earlier run left half-written removed as the storage opens, and only under an id that is a file name of its own; `settled` waits for the writes asked for so far; `memoryTextStorage` keeps them in memory, for tests. `textOf` takes a session's state's messages, the user's and the agent's, in order, without the agent's thinking, and `matchOf` tells whether a title and a text together hold every word of a query, with the passage where the first word the text holds appears, cut short on either side. `shared/search.ts` splits a query into its words, in both processes.
- The window's contract (`shared/sessions.ts`): `SessionSummary`, what the lists show of a session, closed while it is not running, with its latest activity, whether it is archived, its parent for a child, and since when it has been waiting on the user while it is: its oldest open request's time, an operation's approval that the toolset waits on counting as a request; `SessionList`, what the lists show of the sessions: the Sessions list's, how many are archived, and the others whose pages the window has shown; `SessionSettings`, the settings a session runs with; `StartRequest`, what a session page starts a session with, and `ResumeRequest`, what it resumes one that is not running with; `SessionAction`, what a session's menu does; `SessionSearch`, what a search finds among the sessions of one list, with their passages, and how many of them the app has not read; `RememberedChoice`, a folder's last settings, and `FolderChoices`, every folder's and the day folders'; `SessionSnapshot`; and `SessionsBridge`, what the window asks of the sessions through the preload bridge: the list, the archived sessions, resuming a session that is not running with its next message, a session's menu, what the menu would do without it, searching a list, the providers, gateways and models, the remembered settings and remembering them, starting a session with its first message, messages with their images, stops and switches, snapshots, reading a history ahead and events, copying a message's text or an image, saving an image, and an image's menu (`ImageAction`).
- The window's part (`renderer/`):
  - `SessionsSection`, the sidebar's Sessions section, with New session just after its heading and, while there are folders to choose, a filter just after New session, the ui module's `Select`, which starts in the same place whatever it shows, says All there while it chooses none, and narrows the list to the sessions in one folder or below it; then a magnifying glass, which opens a search field, the ui module's `SearchField`, in the filter's place with the focus in it. A search narrows the list further, within the folder chosen, to the sessions whose title or conversation holds every word of the query, as the main process finds them (`useSessionSearch` in `renderer/use-search.ts`, which asks once typing pauses, and asks again every two seconds while the main process still reads sessions for searching; until the answer to the query as it is now comes, the list stays as it was, its answer to the query typed before standing while this one grew or shrank from it), saying how many sessions it has yet to read, or, once the main process knows it, that none match; Escape, or leaving the field empty, closes it and shows the filter again. The heading's row keeps its height whatever it shows, its items on one centre line. Each session shows its status as a dot and in words for VoiceOver, its title or else its provider's name, and its folder's name, with the path in the tooltip; a child shows beneath its parent, indented, the children following their parent the most recently active first, and on its own where the filter or a search leaves its parent out (`nested`), each row telling VoiceOver its level; a click or Return shows it, a press goes to the app module, which drags it elsewhere with the pointer, so that no row starts a drag of the system's, and a secondary click or VoiceOver's menu command offers its menu. The history of a session that is not running is read ahead once, as a press on its row begins, or once the pointer or the keyboard focus has stayed on the row for 150 ms, so that a pointer passing over the list reads nothing. The rows lie in a scroll area of their own that renders only those in view, 28 px each, and eight on either side, taking 40 to be in view until it is measured, as while it is out of sight; each row tells VoiceOver where it lies in the whole list, and the row with the keyboard focus stays while it is scrolled out of view. Without sessions the section shows its heading row alone. Which sessions it shows, those not archived, New session, showing a session, dragging it, reading ahead and its menu are the app module's to decide.
  - `ArchivedButton` and `ArchivedPanel` (`renderer/archived-panel.tsx`), the archived sessions: a button for the title bar with an archive icon, named in its tooltip and for VoiceOver, which opens their panel, and keeps its place, disabled, while there are none; and the panel's body, which loads them through the bridge as it shows and again whenever how many there are changes, with a search field at its top that searches them as the Sessions list's does, then the sessions, the most recently active first, in rows of two lines of which only those in view are rendered. A row shows the session's status, its title or else its provider's name, and how long ago it was last active, in the window's language, and under them its folder and provider or, while a search matches its conversation, the passage that matched, the query's words in ink. A click or Return shows the session and a secondary click offers its menu; the pointer or the keyboard focus on a row brings out Unarchive and Remove from List in place of the time. The panel says when there are no archived sessions, none that match, or how many it has yet to read for searching. `renderer/rows.ts` holds what both lists share: the rows a scroll area renders (`useVisibleRows`), each row reading its session's history ahead as the user reaches for it (`useReadAhead`), and a folder's name.
  - `SessionPage`, a session page: before its first message it chooses the provider, gateway, model, reasoning effort, permission mode and sandbox level, the gateway only where the provider has gateways and the effort only for a model that takes it, and nothing runs; sessions start in auto and workspace-write. The model starts as the one the provider uses when a session chooses none, under its own name where the provider says which it is and otherwise as Default. The effort starts at medium wherever the model takes it, whatever the provider's own default, else at the model's own default where the provider names it, else at the level the model takes nearest medium, the lower of two as near (`startingEffort` in `shared/efforts.ts`); the effort's choices are the model's levels alone, never a default, and a session without an effort shows the model's own default where the provider names it, or else the starting effort, which the host sets for a running session; each level shows with a capital, as the other settings do, such as Medium. Until the provider's models come, the page says it is loading them, and a session started before they come keeps the provider's own defaults. Until the user changes one, the settings are those the folder's sessions last used, but for the permission mode: a model the provider no longer offers gives way to its default, an effort the model does not take to the starting effort, and a provider the app no longer offers, or a gateway that is gone, to the first choice or the provider's own configuration. The provider prefers a sign-in: the folder's remembered provider gives way to a signed-in one where the app knows it is signed out, with that provider's own defaults in the folder's sandbox, and a folder without one starts with the first signed-in provider in the provider menu's order, else Claude Code; until the user picks a provider or types, a sign-in the app learns later changes it (`AccountViews.signedIn`). The settings a session starts or resumes with, and each switch that takes, are remembered for its folder, or for all the day folders when it is one. The settings show under the composer as a row of the ui module's compact selects while the row has room for them on one line, and otherwise as one button, naming the provider, the gateway once one is chosen, the model, effort, mode and sandbox level, whose dropdown, a sheet of the window's paper as the ui module draws one, holds them all, as wide as they need and to the left of the button where the window has no room on its right (`SessionSettings` in `renderer/session-settings.tsx`); the row stays laid out out of sight, so that its width says when it fits again. The first message starts the session, and from then on the page is the session, showing its activity, with everything but the provider still switchable; until the session's state comes, its settings are those it started with, and those of a session the page did not start show nothing, rather than the defaults they would change from. Choosing yolo asks the user to confirm; a running session's sandbox level switches at once. The composer, whose placeholder, Message, is fainter than the settings under it, sends with Return, with the images going with the message, during a turn too, and starts a new line with Shift-Return, leaving Return to an input method while it composes; Stop ends the running turn; how much of the context window the conversation takes shows near the right end of the divider above the composer, with a short stretch of the divider after it, as the tokens in use against the window's size each in whole thousands, with their share of it, such as 25k / 200k (12.5%), or as the tokens alone where the provider gives no size, and in exact numbers in its tooltip. When many items come at once, as a history does, the page renders the last of them first, 24 more at a time before the window paints until they fill its view, and the rest behind them in a render that leaves the window free, so that the end shows at once. A session that is not running, of an earlier run or whose provider stopped, shows its history, saying that it is being read only once that has taken 300 ms, and when it could not be read, and starts nothing: its settings, but for the provider, are those it last had, its permission mode among them, yolo too, until the user changes them, which switches nothing and asks before yolo, and the next message resumes it with them, the message showing after the history while the session resumes; a message that could not resume it comes back to the composer, and the page says so. What it shows of the providers' accounts comes from `AccountViews`, which the app module gives: the provider choice marks a provider known not to be installed, or not to be signed in, the activity begins by saying so with the provider's sign-in while the page's provider is not, or with the progress of the download of the app's copy while one goes on (ADR-0039), a provider not installed giving way, as one signed out does, to a signed-in one on a new page, and the divider above the composer holds the provider's notice of its usage limits before the context in use. Lines that whoever composes the page gives it go above the composer's divider (`aboveComposer`), such as what the session's tools use; for a child, whoever composes the page gives its parent's title (`parentTitle`), which names the sender of its first message.
  - `Timeline` (`renderer/timeline.tsx`), a session's activity as the reference's panes show it, oldest first, in small monospaced type: its messages; each tool call as one entry (`Entry`, the line that opens it, which the approvals module's answered requests share), the approvals and questions as the page's composer renders them (`renderRequest`, told which is the session's oldest waiting request), under a tool call what the composer gives for it by the provider's id for the call, such as a presentation the call made (`renderToolExtra`, which reaches the calls through a context, so that what it shows changing renders no entry again), in place of a call's own entry what the composer gives for it instead, such as what the app's browser and computer tools did, the call's own entry staying where it gives nothing (`renderToolCall`, through a context as well), errors, the notices of new messages from other sessions, each with an inbox icon, its sender in the ink and its summary, in faint type, as the app's (ADR-0036), a child's first message named as its parent's (`firstFrom`), a message on its way while the session starts or resumes, what waits on the user apart from the provider's requests, such as the approvals the app asks for its tools' operations (`hostRequests`), then the agent's task list with finished rows struck through and the current one bright, and Working while a turn runs, or while the session starts or resumes, with the provider's retry of a failed request to the model under it while it retries, in faint type: which retry it makes, of how many where the provider says, and why, in the provider's words, on three lines at most and whole in its tooltip, such as Retrying, attempt 3 of 15: API error (status 500 Internal Server Error); rendering its items from the one the page gives. The page keeps its end in view as it grows, and as what it shows changes size after it renders, such as images loading, until the user scrolls up. Each entry renders again only when its item changes, or a request's when its renderer or whether it is the oldest waiting does, so that a reply as it streams leaves the entries before it as they are, their changes' line counts among them; a change of language still reaches every entry.
  - `Message` (`renderer/message.tsx`), one message: the user's at the right with its images above its text, one another session sent in the user's place named for that session faintly above it and for VoiceOver (`from`), and the agent's at the left with its images below, each in a bubble filled with the darker paper (the ui module's `paper-bubble`) and drawn without an outline, at most 88% of the width and named for VoiceOver by its sender, and the agent's thinking, its reasoning summaries, quieter, under a dashed line instead of in a bubble. A message shows as Markdown, with the ui module's renderer (`renderer/markdown.tsx` gives it the message's thumbnails) or as plain text, the agent's and its thinking as Markdown at first and the user's as plain text. MD or TXT, which switches, and Copy, which puts its text on the clipboard, show while the pointer or the focus is on the message, near its top end: on a bubble, as a tab of the bubble's paper over its top edge; above thinking, over its line, which a mask lets give way beneath them, as the context in use sits in the divider above the composer. Out of the flow, they never widen a short bubble, and over the agent's they reach out to the empty side. Markdown shows an image the message carries in a data URL as the timeline's other images, and one elsewhere, unfetched, as a link to it; it sets math with KaTeX, in any of the delimiters models write, a single dollar counting only by Pandoc's rules (`renderer/math-delimiters.ts`), and highlights code whose block names its language with highlight.js, in the tokens' syntax colours (ADR-0010); a table keeps its columns' alignment.
  - The automation of the app's browser and computer tools (`renderer/automation-call.tsx`, `renderer/automation-line.tsx`, ADR-0027), which the app module gives the page from main's automation snapshot. `AutomationCall` shows a call in place of the provider's entry for it: what it did, its words in the ink and what it did it to, a page's host and path or a control's label, apart in small type in the line's colour, such as Opened example.com/pricing or Clicked “Save Draft”; an application or a window is named in the words, as Looked for Mail’s windows. The call that opens a page carries how the page is shared (No sharing, App sign-ins, or Chrome with its profile) and in dashed tags whether a panel showed the page as the call was made (In a panel) or it ran in the background. A script is named by the page it ran on, as Ran a script on example.com/pricing, and opens to show the script and what it came to, its value as JSON, no value or the error it threw, which the line says too (Threw an error). What came of it follows the title: nothing for an effect that was checked, Effect not checked for one sent without a check, Stopped, may have happened, or why it was refused, with the denial's own words; a call refused or stopped part-way shows a sign in the wait colour in place of its kind's, and a click a pointer. Under it, each on a line of its own, what happened on the way, such as a dialog the page opened being dismissed, with the page's sharing, or an application coming to the front, in the wait colour, with the control that opened its window where the record names it; then the screenshots it took, each a small frame of its top in a well under a dashed line, enlarging as other images do, read through the app only once the call shows and again as it takes more, or a line saying they are no longer kept or could not be read. The browser tools and the computer tools are named by their deeds, an action by its kind and the control it named, also where it was refused or stopped, and a computer action with its application in a tag, as Clicked “Save Draft” with Mail; a sandbox refusal names the level the call ran in, as Not allowed in Read-only; any other tool by its own name. `AutomationLine`, while the session uses tabs or applications, is the rows above the composer's divider, in small faint type, one for each tab and one for each application with all of its windows: a dot, live while the tools work there and in the wait colour while they wait, pause or stop, then the words for what the session does there (Using, Waiting for your answer to use, Paused in, Stopping in) with the tab's host or the application's name in the ink, the tab's sharing and whether a panel shows it (in a panel) or it works in the background, or the application's background or foreground; Show, while no panel shows the row's target, presents it, and a tab's Close closes it, ending the agent's use of it, its operation and grants included, whoever has the tab, and closes the panels that show it; both are small outlined buttons that tell VoiceOver which tab or application they act on. The rows offer no Stop, since the composer's Stop stops the session's turn and with it its browser and computer work. What could not be shown or closed, they say. `GrantsLine` (`renderer/automation-grants.tsx`), while the session holds grants, is a line of the same kind under it: a live dot, how many grants in the ink, and what each lets the agent use, as Chrome tab mail.example.com or Mail in the foreground; Show opens a sheet of the window's paper above it that lists each grant with its kind in a dashed tag, its page or application, for this operation or this session, and End, which ends it at once. While the sheet is open, the button reads Hide and closes it; the sheet also closes as a menu does, and lies over the page, so that a web page in a panel shows still beneath it. `renderer/automation-labels.ts` holds the words' rules: a target's name, the sharing tag, the delivery and a call's state and note.
  - `Images` and `Thumbnail` (`renderer/images.tsx`), images in a message, in what a tool call returned, or going with the message being written: thumbnails that keep their proportions, or for the app's tools' screenshots (`shot`) a small frame of the image's top in a well under a dashed line, which a double click, or Return or Space, shows enlarged over the window until Escape, a click beside it or a double click; a right click or the menu key offers Copy Image, which copies it as a PNG, and Save Image As…, which saves it as it is. What the timeline does through the bridge, copying and an image's menu, comes from `TimelineActionsContext` (`renderer/timeline-actions.ts`), which each page provides.
  - `useAttachments` and `Attachments` (`renderer/attachments.tsx`), the images going with the message being written: pasted into the composer, beside any text the paste carries, or dropped on the composer, which keeps the drop from opening them in panels and is marked while they are dragged over it; there is no button to choose files. Each shows as a small thumbnail with a button that takes it out. `readImage` (`renderer/image-input.ts`) takes an image as it can go to every provider: a larger one is scaled down to 2,000 px, a GIF then becoming a PNG, and one still too large becomes a JPEG; an image of another type, too large even so, or unreadable, or one beyond ten, leaves a notice. A message of images alone goes too; one that cannot be sent comes back to the composer, images included.
  - `ToolCall` (`renderer/tool-call.tsx`), a tool call as one entry from its start to its end: a line with an icon of its kind in the colour of its state (for a call of the app's own browser or computer tools, the icon and the name for VoiceOver that the app's record of the call shows once it takes the entry's place: a globe, a screen or, for a click, a pointer), what it works on, a call of an MCP tool by what it did rather than by its provider's name for it (one of the app's own tools in the app's words, such as Sent a message: Tests pass, with what it acted on apart in small type, and another server's by the server and the tool's name in words, such as github · create issue), the lines its changes add and remove, and Failed if it failed, with its kind and state in words for VoiceOver. `Entry`, its line, also takes a title drawn in parts, short facts in dashed tags, a note in place of the state, and `attention`, which draws the icon in the wait colour and the title as any other's, as for a call refused or stopped part-way. A file is named once: in the line when the call changed one file, above each diff when it changed several. The providers and every list of models found are kept, as the host keeps them; a page before its first message asks for the models in its folder fresh as it opens, since the provider's settings may have changed since, and shows the list kept for its folder, or else the one without a folder, until they come, while a session's page, which shows the model the session last ran, takes those found without a folder; gateways are asked for again whenever a page needs them; a list that failed shows as empty unless the page already shows one, without hiding a fallback list that arrives later; a successful empty folder catalog stays empty, and a failed listing is asked for again when a page next needs it. It also keeps the settings each folder's sessions last used, which `preloadOffers` asks for too: `useRemembered` gives a folder's, or the day folders' in a day folder, without a provider the app no longer offers and without a gateway that is gone, and `rememberChoice` keeps a session's for the window's pages at once and in the app's data.
  - `useSessions` keeps what the lists show current through the bridge, telling its caller of each session a change names as removed, so that its panels close at once, and `useSession` one session's state: the snapshot, then each event folded the same way, skipping those the snapshot holds.

## Not responsible for

- Speaking a provider's protocol: each adapter maps its provider onto this model (ADR-0005).
- Creating the adapters and the toolset: the app module does, and hands the providers to the host.
- Carrying calls and events between the window and the main process: the app module's preload bridge does.
- Which folders the filter offers, and where New session, a shown session and the archived sessions open: the app module decides, and the panel area holds session pages, sessions and the archived sessions' panel.
- Answering approvals and questions in the window, and the waiting indicator, which the approvals module does.
- Sessions started in a provider's own tools, which the app neither loads nor lists.
- Credentials: providers sign in through their own tools, and nothing here reads or carries a key or token (ADR-0028).

## Interface

- From `main/provider.ts`, for adapters, the toolset and the main process: `Provider`, `ProviderSession`, `StartOptions`, `ResumeOptions`, `SessionEventListener`, `Toolset` and `ToolsetAccess`.
- From `main/host.ts`, `main/native.ts`, `main/choices.ts`, `main/records.ts`, `main/inbox.ts` and `main/folders.ts`, for the app module: `SessionHost` with `SessionsMenuUi`, `windowSessionsUi` and `SessionsUi`, `copyText` and `copyImage`, `RememberedChoices` with `choiceStorage`, `SessionRecords` with `recordStorage`, `SessionInboxes` with `inboxStorage`, `textStorage`, and `dayRoot`, `dayFolder` and `makeDayFolder`.
- From `main/provider.ts`, for the toolset and the app module: `SessionCoordinator`, `CoordinatedSession`, `ChildRequest`, `ChildModels` and `InboxEntry`.
- For both processes: the types in `shared/events.ts`, what `shared/efforts.ts`, `shared/inbox.ts` and `shared/tools.ts` hold, `applyEvent`, `initialSessionState`, `sessionStatus` and `openRequests` from `shared/session-state.ts`, the types in `shared/sessions.ts`, `isDayFolder`, `choiceIn` and `withChoice` from `shared/folders.ts`, what `shared/images.ts` holds, and `searchWords` from `shared/search.ts`.
- For the app module's renderer: `SessionsSection` and `SessionFolder` from `renderer/sessions-section.tsx`, `ArchivedButton`, `ArchivedPanel` and `ArchivedAction` from `renderer/archived-panel.tsx`, `SessionPage` and `AccountViews` from `renderer/session-page.tsx`, `statusDots` from `renderer/timeline.tsx`, `preloadOffers` from `renderer/use-offers.ts`, and `useSessions` from `renderer/use-sessions.ts`.
- What an adapter must keep to:
  - `start` and `resume` resolve once the provider's session id is known, and the listener receives every event from the first.
  - `resume` replays the session's past events through the same listener, then reports `replay-finished`. `history` gives the same past events without resuming the session: no turn runs, nothing is sent to the session and nothing of it stays open.
  - `send` reports the user's message at once and resolves once the provider has accepted it. While no turn runs it starts one; during a turn the message goes to the running turn where the provider takes it there, or else starts a turn of its own after the running one, together with any others sent meanwhile. `turn-started` and `turn-ended` frame each turn, a turn the provider starts by itself for such messages included.
  - Every approval and question ends with `request-resolved`; `interrupt`, the end of the turn and `closed` resolve whatever is still open as cancelled. A question answered by message (`byMessage`), where the provider takes the answer as the user's next message, is the exception: only `closed` cancels it, the answer goes out as the user's next message, as `send` sends one, and a message of the user's own resolves it as answered.
  - `canAllowForSession` is true only where the provider itself can remember an approval for the rest of the session.
  - A call of an MCP tool carries `mcp`, the server and tool as the provider names them, the app's own toolset as `TOOLSET_NAME` whatever the provider calls it, with the call's arguments given to `mcpCall`; a tool of the provider's own is titled by what it acts on, or else by its name in words.
  - `writeTitle` runs no tools, changes no session and leaves no session in the provider's history: a turn that starts a tool fails. `setTitle` gives the title where the provider keeps it, and reports it as the session's title.
  - The host context's notices of new messages go in a block of their own beside the presentation state, never in the user's text, and their delivery is accepted as the provider takes the message. `deliverContext` starts a turn with the host context alone, reports `turn-started` and no message of the user's, and refuses while a turn runs. The provider's history gives a block of notices back as an `inbox` event.
  - File changes are unified diffs, built from whatever form the provider reports them in, and name the tool call that made them, with which the timeline shows them.
  - `send` takes the message's images, of a type and size every provider takes, and reports them with the user's message; images the provider gives, in the agent's messages, in what a tool call returned or in a replayed message, are reported with them, in base64 with their media type.
  - The agent's reasoning reaches the timeline as thinking wherever the provider gives it: its summaries, as each provider's own configuration has them.
  - The answer to a question marked `secret` is typed into a masked field and never stored or logged.
  - A null gateway stands for the provider's own configuration, a null model or effort for the provider's default. `settings` reports the session's current choices and `models` what it can switch to.
  - `listModels` finds a gateway's models without starting a session, so nothing appears in the provider's history. It is given the folder a page would start the session in, which may not exist yet, and runs nothing there: a provider counts the folder's own settings only where it can read them so, as Codex's `config/read` does. It marks the model a session uses when it chooses none as the default, and gives each model its own default effort, wherever the provider says which they are; it adds no default of its own beside the provider's.
  - `retrying` reports each retry of a failed request to the model that the provider says it makes during a turn, with the retry, counted from 1, how many it makes at most and why, in the provider's words, as far as the provider gives them. No event reports the end of the retries: the agent's next output, approval or question, or the turn's end, ends them in the state.
  - `context` reports how many tokens of the model's context window the conversation takes, with the window's size where the provider gives it, whenever the provider counts it anew; `title` reports the title the provider keeps for the session, whether the user gave it or the provider wrote it.
  - `setGateway` asked for during a turn takes effect when the turn ends, before the next one. Across a switch the session keeps its id and its history, and reports no `closed`.
  - A sandbox level has one configuration whatever the permission mode, and changing one of the two never changes the other. `setSandbox` takes effect at once where the provider allows it, and otherwise from the next turn. A resumed session takes the settings it is given, which the app keeps for it, its sandbox level among them.

## Dependencies

- `main/` and `shared/` use no other module, but for `main/native.ts`, which uses Electron's save panel and clipboard, Node.js built-ins, the i18n module and the ui module's prompts; `main/host.ts` uses Node.js built-ins, and `main/choices.ts` and `main/records.ts` electron-store and zod (ADR-0039). `shared/` imports no main-process or renderer code, no Node.js built-ins and no Electron, so it runs in both processes; it is type-checked against both the Node.js and the browser configuration.
- `renderer/` uses the ui and i18n modules, React and react-i18next; its Markdown comes from the ui module (ADR-0010, ADR-0018).
- Never imports a provider adapter, the toolset, the workspaces or the app module. The rules `sessions-not-to-providers`, `sessions-only-to-ui-and-i18n`, `toolset-only-from-app`, `app-is-the-entry` and the `shared-not-to-*` rules in `.dependency-cruiser.js` enforce this.

## Invariants

- Events, requests, answers, summaries and the state are plain JSON-serializable data.
- Text from agents and providers is data to show, never UI copy.
- A session page starts nothing until its first message, and a session that is not running nothing until its next message; yolo is entered only once the user confirms it, for a new session or for one that ran in auto, and a session resumes in yolo only when the user chose it for that session before (ADR-0006).
- The host's unit tests drive it with a fake provider in real folders (`main/host.test.ts`), with the records in memory, and the remembered settings and the records are kept in a throwaway folder (`main/choices.test.ts`, `main/records.test.ts`); the session texts and the inboxes are kept in a throwaway folder (`main/texts.test.ts`, `main/inbox.test.ts`); titles' timing, prompt and cleaning and the efforts are pure (`main/titles.test.ts`, `shared/efforts.test.ts`); the section with its search, the archived sessions' panel, the page, its settings, the timeline, with how few of its entries render again as a reply streams, its messages, tool calls, diffs and images, `useOffers` and `useSession` are rendered with fixed sessions or a fake bridge (`renderer/*.test.tsx`), with images read without a canvas, which the tests' document lacks.
