## Responsibilities

- The provider interface (`main/provider.ts`), which each adapter under `src/providers/` implements: `Provider` starts and resumes sessions, with a gateway, a model, a reasoning effort and a sandbox level when chosen, reads a past session's history without resuming it, and lists a folder's past sessions, the gateways set up in the provider's own settings and the models a session could use; `ProviderSession` sends the user's messages, with their images, interrupts the running turn, answers approvals and questions, switches the permission mode, the model, the reasoning effort, the sandbox level and the gateway, and closes the session. Every provider offers the same two permission modes, `auto` and `yolo`, and sessions start in `auto` (ADR-0006). Every provider also offers the same three sandbox levels on its own sandbox, set independently of the mode: `read-only`, `workspace-write`, in which the agent writes only in the session's folder and in temporary folders, and `full-access`, without a sandbox; sessions start in `workspace-write`.
- The event model (`shared/events.ts`): the `SessionEvent` union a session reports (turns; streamed messages, with their images; tool calls, in the Agent Client Protocol's tool kinds and statuses, with the images they return; the agent's task list; file changes as unified diffs; approvals and questions and their resolution; title, mode, the session's gateway, model, reasoning effort and sandbox level, the models it can switch to, the end of a replay, how much of the context window the conversation takes, errors, closing; and two of the host's own, which no provider sends: the history it read for a session that is not running, and that session's resumption), together with the requests, answers, history entries, permission modes, sandbox levels and model options, which mark the model a session uses when it chooses none and each model's own default effort. An image (`MessageImage`) is its media type and its bytes in base64; `shared/images.ts` holds what a message can carry to every provider, as Claude's API, the strictest, takes it: PNG, JPEG, GIF or WebP, at most 10 images, each at most 2,000 px on its long edge and 5 MB in base64, and tells an image's type from its first bytes.
- The toolset's contract (`main/provider.ts`, ADR-0012): `Toolset`, which the toolset module implements and the app hands to the adapters that give it to their sessions; and `ToolsetAccess`, the address and credential one session's provider process uses.
- The session state (`shared/session-state.ts`): `applyEvent` folds a session's events into what the UI shows, a timeline in the order things first happened, in which each tool call holds the files it changed, and the current task list; the requests left open at a turn's end are cancelled, but for questions answered by message (`byMessage`), which wait until the session closes; a session's history folds at once, as the session ended, with no turn running and no request waiting, and the state says while it is still to be read and when it could not be; a resumed session runs again with what it showed. `sessionStatus` derives running, waiting, idle or closed, and `openRequests` lists the approvals and questions still waiting, oldest first.
- The host (`main/host.ts`): `SessionHost` runs the sessions started in the app in the main process, through the providers the app module hands it. It starts a session in a folder through its provider, folds the session's events into its state from the first, and lists it once the provider has started it. It passes messages, stops, answers to approvals and questions, which it then records in the session's state without a question's typed answers to secrets (`request-answered`), and switches to the session, offers its providers, their gateways and their models, found once per provider and gateway for the app's run (a list that fails, or that the provider has not found within a minute, is asked for again next time), and gives each session's state as a snapshot counted in events. Until the provider titles a session, its first message, on one line and shortened, stands in for the title. `list` gives what the window's lists show (`SessionList`): the Sessions list, the sessions that are not archived, the most recently active first, a session moving up as the user sends it a message and as a turn of it ends, which holds those the records keep and any that is open, so that beyond the sessions open it never holds more than 1,000; how many sessions are archived, the archived sessions themselves coming only when asked for (`archived`), as the archived list opens; and the sessions whose pages the window has shown in this run, as it asked for their snapshots, that the Sessions list does not hold, archived ones and those the records no longer keep, so that their panels keep what they show. Listeners hear whenever any of that changes, a change to an archived session the window has not shown changing nothing; event listeners hear every event, numbered within its session as the snapshots count them. Every session it starts stays in the records, while they keep it, with the title the list shows, its latest activity, whether it is archived and the settings it has, its permission mode among them, saved as they change; the sessions of earlier runs come back from the records, and sessions started in a provider's own tools are never listed. A session that is not running, one of an earlier run or one whose provider stopped, is listed as closed. The first snapshot of one of an earlier run has its history read from its provider without resuming it (`history`), the settings the history reports left out for those the app kept, and the history follows as one event, or a failure with none. `resume` resumes a session that is not running under the same id, with the settings its page shows, yolo too, since the user chose it for the session (ADR-0006), a gateway no longer set up giving way to the provider's own configuration with its default model and effort; it reads the history first where it has not been read, so that the provider's replay is not shown twice, or else takes the replay as the history, and a session that cannot be resumed stays as it was. A message sent to a session returns it to the Sessions list when it was archived. `archive` moves a session to the archived list and `unarchive` back; `remove` takes it off the lists and out of the records, leaving its provider's history as it is; both close a session while it is open. `showMenu` offers a session's menu through the window's (`SessionsMenuUi`), and asks first before it archives a session that is working, which stops it, and before it removes one. `closeAll` closes every open session as the app quits.
- Confirmations, menus and images (`main/native.ts`): `windowSessionsUi` asks, through the window's prompts (the ui module's `Prompts`, which the window draws in the app's own look, ADR-0013) and in the main process's language, before a session runs in yolo, before a session that is working is archived and before a session leaves the lists, Cancel being the default answer each time; offers the same way a session's menu, Archive, or Unarchive for an archived session, and Remove from List, and an image's menu, Copy Image and Save Image As…, at the pointer; and saves an image where the user chooses in macOS's save panel, as a sheet, Downloads at first. `copyText` and `copyImage` put a message's text, or a PNG image, on the clipboard.
- Day folders (`main/folders.ts`): where a session page opens while no workspace has been added, a folder of the day's date in the day root, `~/3mukon-code`, such as `~/3mukon-code/2026-10-28`, made only when a session starts there, so that a page closed without a message leaves nothing behind. `shared/folders.ts` tells a day folder from any other, in both processes.
- Remembered settings (`main/choices.ts`): `RememberedChoices`, the settings sessions last used, the provider, gateway, model, reasoning effort and sandbox level: each folder's, by the folder's path, for the 200 folders last used, and one set that all the day folders share, kept in `session-choices.json` in the app's data (`choiceStorage`, readable by the user alone). The permission mode is not among them, so that yolo is entered only on the user's choice (ADR-0006). The window gets them for the providers the app offers.
- Records (`main/records.ts`): `SessionRecords`, the sessions the app started, every archived one and of the others the 1,000 active last: each one's id, provider, the provider's id for it, folder, the title the list last showed, its latest activity, whether it is archived and the settings it last had, its permission mode among them, kept in `sessions.json` in the app's data (`recordStorage`, readable by the user alone), so that later runs list them, show their history and resume them as they were; a session removed from the lists leaves them.
- The window's contract (`shared/sessions.ts`): `SessionSummary`, what the lists show of a session, closed while it is not running, with its latest activity, whether it is archived and since when it has been waiting on the user while it is (its oldest open request's time); `SessionList`, what the lists show of the sessions: the Sessions list's, how many are archived, and the others whose pages the window has shown; `SessionSettings`, the settings a session runs with; `StartRequest`, what a session page starts a session with, and `ResumeRequest`, what it resumes one that is not running with; `SessionAction`, what a session's menu does; `RememberedChoice`, a folder's last settings, and `FolderChoices`, every folder's and the day folders'; `SessionSnapshot`; and `SessionsBridge`, what the window asks of the sessions through the preload bridge: the list, the archived sessions, resuming a session that is not running with its next message, a session's menu, the providers, gateways and models, the remembered settings and remembering them, starting a session with its first message, messages with their images, stops and switches, snapshots and events, copying a message's text or an image, saving an image, and an image's menu (`ImageAction`).
- The window's part (`renderer/`):
  - `SessionsSection`, the sidebar's Sessions section, with New session just after its heading and, while there are folders to choose, a filter just after New session, the ui module's `Select`, which starts in the same place whatever it shows and narrows the list to the sessions in one folder or below it. Each session shows its status as a dot and in words for VoiceOver, its title or else its provider's name, and its folder's name, with the path in the tooltip; a click or Return shows it, and a secondary click or VoiceOver's menu command offers its menu. The rows, which the archived list shares (`SessionRows`), lie in a scroll area of their own that renders only those in view, 28 px each, and eight on either side, taking 40 to be in view until it is measured, as while it is out of sight; each row tells VoiceOver where it lies in the whole list, and the row with the keyboard focus stays while it is scrolled out of view. Without sessions the section shows its heading row alone. Which sessions it shows, those not archived, New session, showing a session and its menu are the app module's to decide.
  - `ArchivedSessions` (`renderer/archived-sessions.tsx`), the archived list, for the title bar: a button with an archive icon, named in its tooltip and for VoiceOver, whose dropdown, a sheet of the window's paper as the ui module draws one, kept out of the title bar's drag area, lists the archived sessions as the Sessions list shows its own. It is told how many are archived, and loads them through the bridge only as the dropdown opens, again while it stays open whenever their number changes, and lets them go as it closes; while they load, the dropdown is as tall as their list will be. A session clicked there shows as the dropdown closes, and its menu unarchives or removes it. Without archived sessions the button keeps its place, disabled, and the dropdown, there only while there are some, closes.
  - `SessionPage`, a session page: before its first message it chooses the provider, gateway, model, reasoning effort, permission mode and sandbox level, the gateway only where the provider has gateways and the effort only for a model that takes it, and nothing runs; sessions start in auto and workspace-write. The model starts as the one the provider uses when a session chooses none, under its own name where the provider says which it is and otherwise as Default. The effort starts at medium wherever the model takes it, whatever the provider's own default, else at the model's own default where the provider names it, else at the provider's default, shown as Default; each level shows with a capital, as the other settings do, such as Medium. Until the provider's models come, the page says it is loading them, and a session started before they come keeps the provider's own defaults. Until the user changes one, the settings are those the folder's sessions last used, but for the permission mode: a model the provider no longer offers gives way to its default, an effort the model does not take to the starting effort, and a provider the app no longer offers, or a gateway that is gone, to the first choice or the provider's own configuration. The settings a session starts or resumes with, and each switch that takes, are remembered for its folder, or for all the day folders when it is one. The settings show under the composer as a row of the ui module's compact selects while the row has room for them on one line, and otherwise as one button, naming the provider, the gateway once one is chosen, the model, effort, mode and sandbox level, whose dropdown, a sheet of the window's paper as the ui module draws one, holds them all, as wide as they need and to the left of the button where the window has no room on its right (`SessionSettings` in `renderer/session-settings.tsx`); the row stays laid out out of sight, so that its width says when it fits again. The first message starts the session, and from then on the page is the session, showing its activity, with everything but the provider still switchable. Choosing yolo asks the user to confirm; a running session's sandbox level switches at once. The composer, whose placeholder, Message, is fainter than the settings under it, sends with Return, with the images going with the message, during a turn too, and starts a new line with Shift-Return, leaving Return to an input method while it composes; Stop ends the running turn; how much of the context window the conversation takes shows near the right end of the divider above the composer, with a short stretch of the divider after it, as the tokens in use against the window's size with their share of it, such as 25,000 / 200,000 (12.5%), or as the tokens alone where the provider gives no size. A session that is not running, of an earlier run or whose provider stopped, shows its history, saying so while it is read and when it could not be, and starts nothing: its settings, but for the provider, are those it last had, its permission mode among them, yolo too, until the user changes them, which switches nothing and asks before yolo, and the next message resumes it with them, the message showing after the history while the session resumes; a message that could not resume it comes back to the composer, and the page says so.
  - `Timeline` (`renderer/timeline.tsx`), a session's activity as the reference's panes show it, oldest first, in small monospaced type: its messages; each tool call as one entry (`Entry`, the line that opens it, which the approvals module's answered requests share), the approvals and questions as the page's composer renders them (`renderRequest`, told which is the session's oldest waiting request), errors, a message on its way while the session starts or resumes, then the agent's task list with finished rows struck through and the current one bright, and Working while a turn runs, or while the session starts or resumes. It keeps its end in view as it grows until the user scrolls up.
  - `Message` (`renderer/message.tsx`), one message: the user's at the right in a filled bubble with its images above its text, the agent's at the left in an outlined one with its images below, each at most 88% of the width and named for VoiceOver by its sender, and the agent's thinking, its reasoning summaries, quieter, under a dashed line instead of in a bubble. A message shows as Markdown (`renderer/markdown.tsx`) or as plain text, the agent's and its thinking as Markdown at first and the user's as plain text. MD or TXT, which switches, and Copy, which puts its text on the clipboard, show while the pointer or the focus is on the message, laid over the bubble's top border near its end, or over the line above thinking, as the context in use sits in the divider above the composer; a mask lets the line give way beneath them. Out of the flow, they never widen a short bubble, and over the agent's they reach out to the empty side. Markdown shows an image the message carries in a data URL as the timeline's other images, and one elsewhere, unfetched, as a link to it; it sets math with KaTeX, in any of the delimiters models write, a single dollar counting only by Pandoc's rules (`renderer/math-delimiters.ts`), and highlights code whose block names its language with highlight.js, in the tokens' syntax colours (ADR-0010); a table keeps its columns' alignment.
  - `Images` and `Thumbnail` (`renderer/images.tsx`), images in a message, in what a tool call returned, or going with the message being written: thumbnails that keep their proportions, which a double click, or Return or Space, shows enlarged over the window until Escape, a click beside it or a double click; a right click or the menu key offers Copy Image, which copies it as a PNG, and Save Image As…, which saves it as it is. What the timeline does through the bridge, copying and an image's menu, comes from `TimelineActionsContext` (`renderer/timeline-actions.ts`), which each page provides.
  - `useAttachments` and `Attachments` (`renderer/attachments.tsx`), the images going with the message being written: pasted into the composer, beside any text the paste carries, or dropped on the composer, which keeps the drop from opening them in panels and is marked while they are dragged over it; there is no button to choose files. Each shows as a small thumbnail with a button that takes it out. `readImage` (`renderer/image-input.ts`) takes an image as it can go to every provider: a larger one is scaled down to 2,000 px, a GIF then becoming a PNG, and one still too large becomes a JPEG; an image of another type, too large even so, or unreadable, or one beyond ten, leaves a notice. A message of images alone goes too; one that cannot be sent comes back to the composer, images included.
  - `ToolCall` (`renderer/tool-call.tsx`), a tool call as one entry from its start to its end: a line with an icon of its kind in the colour of its state, what it works on, the lines its changes add and remove, and Failed if it failed, with its kind and state in words for VoiceOver. The line opens and closes the entry from the pointer and the keyboard, with a chevron at its end; opened, the entry shows the diff of each file the call changed, or else the images the call returned, and its command and its output. A file is named once: in the line when the call changed one file, above each diff when it changed several. A file change no tool call made is an entry of its own (`FileChangeEntry`). `DiffView` (`renderer/diff-view.tsx`) shows a unified diff as its lines, each after its numbers in the file before and after the change, the added lines on a green tint and the removed ones on a red one, with a gap between hunks; long lines wrap, a long diff scrolls within the view, and at most 1,000 lines show, with how many are left out.
  - `useOffers` (`renderer/use-offers.ts`) gives a session page what it offers to choose from, kept once per window for all its pages: the providers, each provider's gateways and the models of each provider and gateway. `preloadOffers` asks for them as the window opens: the providers, then each one's gateways and the models of its own configuration, so that a page shows them as it first appears. The providers and every list of models found are kept, as the host keeps them; gateways are asked for again whenever a page needs them; a list that failed shows as empty and is asked for again when a page next needs it. It also keeps the settings each folder's sessions last used, which `preloadOffers` asks for too: `useRemembered` gives a folder's, or the day folders' in a day folder, without a provider the app no longer offers and without a gateway that is gone, and `rememberChoice` keeps a session's for the window's pages at once and in the app's data.
  - `useSessions` keeps what the lists show current through the bridge, and `useSession` one session's state: the snapshot, then each event folded the same way, skipping those the snapshot holds.

## Not responsible for

- Speaking a provider's protocol: each adapter maps its provider onto this model (ADR-0005).
- Creating the adapters and the toolset: the app module does, and hands the providers to the host.
- Carrying calls and events between the window and the main process: the app module's preload bridge does.
- Which folders the filter offers, and where New session and a shown session open: the app module decides, and the panel area holds session pages and sessions.
- Answering approvals and questions in the window, and the waiting indicator, which the approvals module does.
- Sessions started in a provider's own tools, which the app neither loads nor lists.
- Credentials: providers sign in through their own tools, and nothing here reads or carries a key or token (ADR-0008).

## Interface

- From `main/provider.ts`, for adapters, the toolset and the main process: `Provider`, `ProviderSession`, `StartOptions`, `ResumeOptions`, `SessionEventListener`, `Toolset` and `ToolsetAccess`.
- From `main/host.ts`, `main/native.ts`, `main/choices.ts`, `main/records.ts` and `main/folders.ts`, for the app module: `SessionHost` with `SessionsMenuUi`, `windowSessionsUi` and `SessionsUi`, `copyText` and `copyImage`, `RememberedChoices` with `choiceStorage`, `SessionRecords` with `recordStorage`, and `dayRoot`, `dayFolder` and `makeDayFolder`.
- For both processes: the types in `shared/events.ts`, `applyEvent`, `initialSessionState`, `sessionStatus` and `openRequests` from `shared/session-state.ts`, the types in `shared/sessions.ts`, `isDayFolder`, `choiceIn` and `withChoice` from `shared/folders.ts`, what `shared/images.ts` holds.
- For the app module's renderer: `SessionsSection` and `SessionFolder` from `renderer/sessions-section.tsx`, `ArchivedSessions` from `renderer/archived-sessions.tsx`, `SessionPage` from `renderer/session-page.tsx`, `statusDots` from `renderer/timeline.tsx`, `preloadOffers` from `renderer/use-offers.ts`, and `useSessions` from `renderer/use-sessions.ts`.
- What an adapter must keep to:
  - `start` and `resume` resolve once the provider's session id is known, and the listener receives every event from the first.
  - `resume` replays the session's past events through the same listener, then reports `replay-finished`. `history` gives the same past events without resuming the session: no turn runs, nothing is sent to the session and nothing of it stays open.
  - `send` reports the user's message at once and resolves once the provider has accepted it. While no turn runs it starts one; during a turn the message goes to the running turn where the provider takes it there, or else starts a turn of its own after the running one, together with any others sent meanwhile. `turn-started` and `turn-ended` frame each turn, a turn the provider starts by itself for such messages included.
  - Every approval and question ends with `request-resolved`; `interrupt`, the end of the turn and `closed` resolve whatever is still open as cancelled. A question answered by message (`byMessage`), where the provider takes the answer as the user's next message, is the exception: only `closed` cancels it, the answer goes out as the user's next message, as `send` sends one, and a message of the user's own resolves it as answered.
  - `canAllowForSession` is true only where the provider itself can remember an approval for the rest of the session.
  - File changes are unified diffs, built from whatever form the provider reports them in, and name the tool call that made them, with which the timeline shows them.
  - `send` takes the message's images, of a type and size every provider takes, and reports them with the user's message; images the provider gives, in the agent's messages, in what a tool call returned or in a replayed message, are reported with them, in base64 with their media type.
  - The agent's reasoning reaches the timeline as thinking wherever the provider gives it: its summaries, as each provider's own configuration has them.
  - The answer to a question marked `secret` is typed into a masked field and never stored or logged.
  - A null gateway stands for the provider's own configuration, a null model or effort for the provider's default. `settings` reports the session's current choices and `models` what it can switch to.
  - `listModels` finds a gateway's models without starting a session, so nothing appears in the provider's history. It marks the model a session uses when it chooses none as the default, and gives each model its own default effort, wherever the provider says which they are; it adds no default of its own beside the provider's.
  - `context` reports how many tokens of the model's context window the conversation takes, with the window's size where the provider gives it, whenever the provider counts it anew; `title` reports the title the provider keeps for the session, whether the user gave it or the provider wrote it.
  - `setGateway` asked for during a turn takes effect when the turn ends, before the next one. Across a switch the session keeps its id and its history, and reports no `closed`.
  - A sandbox level has one configuration whatever the permission mode, and changing one of the two never changes the other. `setSandbox` takes effect at once where the provider allows it, and otherwise from the next turn. A resumed session takes the settings it is given, which the app keeps for it, its sandbox level among them.

## Dependencies

- `main/` and `shared/` use no other module, but for `main/native.ts`, which uses Electron's save panel and clipboard, Node.js built-ins, the i18n module and the ui module's prompts; `main/host.ts` uses Node.js built-ins, and `main/choices.ts` and `main/records.ts` electron-store and zod (ADR-0004). `shared/` imports no main-process or renderer code, no Node.js built-ins and no Electron, so it runs in both processes; it is type-checked against both the Node.js and the browser configuration.
- `renderer/` uses the ui and i18n modules, React, react-i18next, react-markdown with remark-gfm (ADR-0004), and remark-math, rehype-katex with KaTeX's stylesheet and fonts, and rehype-highlight (ADR-0010).
- Never imports a provider adapter, the toolset, the workspaces or the app module. The rules `sessions-not-to-providers`, `sessions-only-to-ui-and-i18n`, `toolset-only-from-app`, `app-is-the-entry` and the `shared-not-to-*` rules in `.dependency-cruiser.js` enforce this.

## Invariants

- Events, requests, answers, summaries and the state are plain JSON-serializable data.
- Text from agents and providers is data to show, never UI copy.
- A session page starts nothing until its first message, and a session that is not running nothing until its next message; yolo is entered only once the user confirms it, for a new session or for one that ran in auto, and a session resumes in yolo only when the user chose it for that session before (ADR-0006).
- The host's unit tests drive it with a fake provider in real folders (`main/host.test.ts`), with the records in memory, and the remembered settings and the records are kept in a throwaway folder (`main/choices.test.ts`, `main/records.test.ts`); the section, the archived list, the page, its settings, the timeline, its messages, tool calls, diffs and images, `useOffers` and `useSession` are rendered with fixed sessions or a fake bridge (`renderer/*.test.tsx`), with images read without a canvas, which the tests' document lacks.
