## Responsibilities

- `NativeHelper` lazily starts the app-owned helper with private inherited pipes. `main/install-helper.ts` keeps the packaged bundle's copy in the app's data folder, replaces it where it differs, and checks the signature of what runs (ADR-0033). The first reply must match the protocol version, a fresh generation and the child's PID. The helper holds its own macOS permissions (ADR-0033): as it starts, it starts itself again in place, so that macOS holds it and not the app responsible for what it does, and ends where it cannot. Permission replies read macOS Accessibility, Screen Recording and Input Monitoring status through preflight queries.
- Calls have bounded frames and deadlines. The helper reads each complete frame as its bytes arrive on the open pipe. One command runs at a time, with duplicate setup and discovery reads coalesced. Cancellation is sent separately while the command is running. A malformed reply, timeout or exit retires the generation. Shutdown closes the input pipe and waits for the specific child, with bounded termination escalation. Restart drains the previous generation before checking a fresh one.
- A lost helper connection retires its target handles and records an indeterminate `backend-lost` outcome for a dispatched action. The broker holds the action's exclusion until the child exits and retains the result for matching action ID replays.
- `computer_targets` reports up to 64 running regular macOS applications as names, bundle IDs and owner-scoped discovery IDs. `computer_select` rechecks the selected process and creates an application target. `computer_windows` needs the application's background operation and returns window handles for verified standard windows. The helper uses the process start identity, held AX window reference and WindowServer identity. It excludes the host app and its helper family, sheets and dialogs.
- `computer_observe` returns up to 48 Accessibility controls, with labels and available actions. A text without a label is named by its words, and a part of a window or a scroll bar by what it is. Secure fields are excluded. An explicit image request also needs Screen Recording and image support in the provider. It captures a single verified window with a bounded raster, in a lower quality where its detail would exceed the reply, and returns its scale, geometry and capture time. Secure Input or a secure control seen in the tree blocks the image. The capture can contain visible content within the selected window. [ScreenCaptureKit window filters](https://developer.apple.com/documentation/screencapturekit/sccontentfilter)
- `computer_act` rechecks the app, window, latest observation and receiver before dispatch. Background routes use Accessibility press, field replacement, scroll controls and explicit window changes. A scroll bar that does not scroll itself scrolls through its page parts. A control that has not answered within two seconds may still be at work, and is reported so. A minimized window stays a target and can be read and restored. Point click, point scroll, drag and key press need foreground authority and a target window focused by the user. Pointer input also needs a current image and a matching display layout and hit test. Keyboard input verifies the focused non-secure control. Unsupported routes return a typed outcome. File-destination policy applies before dispatch: at workspace-write, a click, point click, drag or key press is refused as `file-scope-unverifiable`, since the application that receives it decides which files it changes.
- Window moves and resizes require matching Accessibility and compositor geometry for coordinate operations. While those readings differ, the observation is stale and the window handle remains valid. Before sending pointer input, the helper checks that the actual mouse receiver and its Accessibility element both belong to the selected window. [AppKit mouse hit testing](https://developer.apple.com/documentation/appkit/nswindow/windownumber(at:belowwindowwithwindownumber:))
- Computer action records keep the validated action kind and, for a currently observed control, its Accessibility label. Window summaries carry the window title and the owning application's name and scoped reference.
- The native coordinator takes a process write lease for background mutations and a desktop write lease for foreground actions. The host broker also schedules these operations across sessions. Foreground actions monitor unclassified input and Secure Input while control is held. Every posted event has a per-action marker. A held key or button is released when the action ends, including cooperative cancellation. Leases stay held through backend settlement, and uncertain action IDs are not replayed. `computer_release` ends the session's operations on the selected application.
- The renderer part (`renderer/computer-use.tsx`, ADR-0027): `ComputerUseSetting`, the settings' Computer use, with the name under which System Settings lists the helper, Accessibility and Screen Recording, and Input Monitoring only where the helper says noticing the user's input needs it; a permission that is allowed says so after its name, one that is not, or not known yet, offers Open System Settings, one that takes effect once the helper restarts offers Restart Helper, and one that cannot be had says Unavailable. `ComputerSetupNotice` is a session's notice that computer use needs a permission, or the helper to restart, drawn as the session's requests are, its title after a sign in the wait colour, with why and the step that starts it. Both take the steps through whoever composes the window, only from the user's click, and say when a step did not go.
- The computer preview (`renderer/computer-preview.tsx`, `renderer/use-computer-preview.ts`, ADR-0027): `ComputerPreviewPanel` is another application's window in a panel, whose header the app module gives the application's name, the session and whether the work runs in the background or the foreground: a line saying it is a preview that takes no input, with the frame's age, and Switch to, which brings the application forward (`reveal`); the window's latest frame, faded, in a frame; Loading preview… until the first frame; until Screen Recording is allowed, the step that allows it; a window that cannot be taken keeps its last frame, or shows its name and why. While the agent acts in the application a chip under the frame names the session, with Stop, and while the user has control of it, with Hand Back (`hand-back`); the chip's strip stays while the session holds the application. `useComputerPreview` asks main for a frame at once and then each second while the panel shows and the window is visible, keeps the last frame when main is busy or cannot take one, and stops when the panel goes; `ComputerPreviewView` joins it to `ComputerBridge` for the app module.
- `ForegroundControlBar` (`renderer/foreground-control.tsx`, ADR-0027) draws the floating panel's controls. It names the session and application, shows Stop and the registered shortcut, offers Hand Back after user input, and gives Secure Input and self-activation their own states. The helper's panel shows it just above the window it is about and directly above it among the windows on the screen, goes where that goes, and lies at the top of the display for one in full screen (ADR-0034). A takeover leaves it where it is.
- The Swift package pins `PeekabooAutomationKit` under ADR-0025. The patch exposes app-owned coordination-root injection and the audited AX-to-WindowServer identity lookup. It retains the library's locking behavior. The helper combines these with platform Accessibility, ScreenCaptureKit and marked foreground input. Background paths use no window-routed synthetic input.
- The Computer use permission rows share a dashed outline without dividers between them. Allowed uses the theme's green from the settings design. Unavailable uses the theme's error red, and the restart-required label uses muted text.

## Not responsible for

- Grant and sandbox policy belong to the broker. The Settings host owns permission actions. The foreground control window is a separate app and renderer integration.

## Interface

- `shared/helper.ts` defines the `HelperSetup` port and the helper's name in System Settings. `status()` reads cached facts. Settings calls `check()` automatically when it opens and when its window regains focus. The check can start the helper and query its permission status. Where a running helper lacks a permission it needs, the check also reads what a process that starts now has, since macOS gives a running process some permissions only once it starts again, and says that the permission waits for a restart; a refused operation then asks for the restart instead of the permission. Open System Settings calls `request()` first, which has macOS ask the user, since the pane lists the helper only once it has asked, and opens the pane where macOS's own prompt, whose button does the same, is not in front. Restart Helper calls `restart()` on a user action. Permission facts from a failed or incompatible helper are unavailable. `main/launch-helper.ts` composes the production launcher. `main/native-protocol.ts` and `main/helper-wire.ts` define the private pipe protocol, whose version both sides check. Older builds require rebuilding with the intended stable signature.
- `shared/computer.ts` defines the trusted window-preview port. A preview requires an open presentation and captures only its selected window on the active Space. It is rate limited, bounded to 768 pixels on its longest edge, and has its own capture time. It leaves the model's input receipt and authority in place.
- The same trusted port accepts user commands to reveal the selected window, take over and hand it back. It checks the owning session and its open presentation. Stop remains available through the session automation port, including with the preview closed.
- `ControlWindowBridge` in `shared/computer.ts` supplies the hidden renderer with a control revision. The renderer draws the control three times, at rest, with the pointer over its buttons and with them pressed, and returns accessible button labels and positions, in points. Main captures that page alone, drawn at the display's density so that the panel shows it as sharply as the windows around it, and sends the control's bounded picture and each button's two other ones, with the window it is about, to the native panel. A paint can still show the page as it was before, so the page marks each with the revision it shows, and main takes only one of the current revision, without its mark. Foreground input waits for the exact revision and verifies the helper-owned WindowServer window and frame. Pointer classification checks which window receives the event. Stop and Hand Back travel over the private connection independently of the active tool request, and so does the stop shortcut, a hot key of macOS's own that the helper has while a control is current.
- `main/computer.ts` owns native target and observation mapping. App composition registers the tools and delegates target ownership, approvals, scheduling and replay to the shared broker. Foreground state names the session and application and reports whether macOS registers the stop shortcut, as the helper says in its first reply. A control lasts as long as its operation.
- `sh scripts/build-native-helper.sh compile` builds the ARM64 executable in scratch storage without signing or launching it. The build requires macOS and Swift 6.2 or later. The helper runs on macOS 14 or later.
- `sh scripts/build-native-helper.sh bundle` stages the development helper under `out/native`. Provide a stable signing certificate's SHA-1 fingerprint as `APP_NATIVE_HELPER_IDENTITY`. The packaged build uses the same setting to stage an independently signed `Computer Use Helper.app` under `Contents/Helpers`, with its verification fingerprint in the archive. A package built without that signing configuration has no native helper.

## Dependencies

- Session automation facts, Node.js, zod and the locked Swift package graph. The launcher uses the system's `codesign` to check the bundle identifier and certificate before execution.

## Invariants

- The helper receives an app-owned coordination root and a narrow environment. Capability listing uses cached facts. An explicit `computer_targets` call may start the signed helper in order to read metadata. Target operations bind to the helper generation that produced their discovery or window handle. The model receives opaque references and image geometry. Process IDs, window numbers, AX objects and input markers remain private.
- Signed development and local packaged launch, permission preflights, restart, crash retirement and quit passed isolated checks on macOS 27.0.1. Exact capture, input and takeover also depend on the target state and permissions available on the host.
